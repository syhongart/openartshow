# 맨해튼 180m — blend → GLB 자산 변환 (월드11 1단계)

감독 지시 2026-09-16, 카드 판정 «우리 월드 11 로». 감독이 올린
`Manhattan_180m.blend`(29.4MB zstd / 압축 해제 183MB)를 월드11이 열 수 있는 GLB 로
굽는다. **이 회차는 자산 변환까지**다 — 월드11 페이지·런타임은 다음 단계다.

원본 blend 는 **저장소에 넣지 않는다**(29MB·출처가 감독 업로드). 그래서 산출물을
커밋 자산으로 두고 만든 절차를 이 디렉터리로 남긴다 — world8 의
`frontend/assets/worlds/world2-blender-edit.glb` 와 같은 형태다.

## 파일

| 파일 | 하는 일 | bpy |
|---|---|---|
| `extract.py` | blend 를 열어 GLB + 카메라/라이트 JSON + 실측표를 낸다 | 쓴다 |
| `glb_names.py` | 산출 GLB 의 이름에서 `.` 을 없앤다(`.` → `_`) | 안 쓴다 |
| `verify-blocks.py` | blend 블록을 **직독**해 `extract.py` 의 실측을 대조한다 | **안 쓴다** |
| `verify-glb.mjs` | 산출 GLB 를 실제 `GLTFLoader` 로 통과시켜 판정한다 | 안 쓴다 |
| `mesh_hash.py` | 메시 「같음」의 정의(H1~H7). 아래 둘이 공유한다 | 안 쓴다 |
| `analyze-instances.py` | 인스턴싱으로 **얼마나 묶이는지** 실측만 한다 | 쓴다 |
| `bake-instances.py` | 같은 형상을 한 벌로 묶어 GLB 를 굽는다 | 쓴다 |

```bash
python3 scripts/asset/manhattan/extract.py --blend <원본.blend> --report /tmp/r.json
python3 scripts/asset/manhattan/verify-blocks.py --blend <원본.blend> --against /tmp/r.json
node   scripts/asset/manhattan/verify-glb.mjs <자산.glb> --cameras <cameras.json>
```

**넷 다 게이트가 아니다** — CI 에서 안 돈다(bpy 휠이 374MB 이고 원본 blend 가 저장소에
없다). 게이트는 `tests/manhattan-glb.test.ts` 다.

## ⚠ 「bpy 로는 못 연다」는 전제는 틀렸다 — 실측으로 정정됨

원본은 **Blender 5.1**(버전코드 501.30)로 저장됐고 설치된 bpy 는 **5.0.1** 이다. 여는
순간 이렇게 뜬다:

```
Warning: File written by newer Blender binary (501.30), expect loss of data!
```

**그 경고 뒤에 유실된 것은 없다**(2026-09-16). bpy 로 읽은 값과, blend 의 SDNA 블록을
직접 읽는 `blender_asset_tracer`(버전 무관)의 값이 **전부 일치한다**:

| 축 | bpy 5.0.1 | BAT(블록 직독) |
|---|---|---|
| 오브젝트 | 21,417 | 21,417 |
| 타입별 | MESH 21,052 · CURVE 140 · FONT 95 · LIGHT 112 · CAMERA 18 | 동일 |
| 메시 | 19,251 | 19,251 |
| 삼각형(씬) | 1,045,716 | 1,045,716 |
| 정점(메시 데이터) | 620,024 | 620,024 |
| 재질 | 46개 이름 전부 | 동일 |

`verify-blocks.py --against` 가 이 대조를 다시 돌린다(diffs 0 · materialsMatch true).

**왜 이것을 적어 두나**: 경고만 보고 「못 연다」로 규정하면 GLB 를 블록에서 손으로
조립하게 되고, 그 경로는 **UV·재질 노드·텍스처·커브·텍스트를 전부 잃는다.** 경고는
측정이 아니다. 5.1 에서 새로 생긴 필드는 5.0 SDNA 에 없어 읽히지 않으므로, 원본이
갱신되면 이 표를 다시 뜬다.

## 실측 — 산출 GLB

`export_yup`(Z-up→Y-up) · `export_apply`(커브·텍스트를 메시로) · 컬렉션을 부모 노드로 ·
accessor 공유. 세 변형을 같은 원본에서 구웠다:

| 변형 | 바이트 | JSON 청크 | 지오메트리 | 이미지 | 판정 |
|---|---:|---:|---:|---:|---|
| `AUTO`(PNG 그대로) | **95,517,512** (91.09 MiB) | 16.63 MB | 62.87 MB | 16.01 MB | 예산 초과 |
| `--image-format WEBP` | **80,025,408** (76.32 MiB) | 16.62 MB | 62.87 MB | **0.53 MB** | 예산 초과 |
| `--draco` | — | — | — | — | **SIGSEGV** |

셋 다 노드 21,306 · 메시 19,482 · 삼각형 1,322,096 으로 **지오메트리는 동일**하다.

* **이미지 압축은 예산 문제를 못 푼다.** WEBP 가 이미지를 16.01 → 0.53 MB(97% 감소)로
  줄여도 총합은 76 MiB 다 — **본질은 지오메트리 62.87 MB** 이고, 그것은 정점
  1,907,224 개 × (POSITION 12B + NORMAL 12B + UV 8B) 다. 정점이 원본 620,024 의 3배인
  것은 exporter 가 **면마다 법선을 끊기 때문**이고(큐브 8정점 → 24정점), 이 세계는
  대부분 각진 박스다. 즉 줄인 것이 아니라 **정직한 크기**다.
* **Draco 는 이 환경에서 못 쓴다.** bpy 5.0.1 번들 인코더가 같은 지점
  (`Sedan_continuous_pressed_body` 근처, 메시 ~19,486개 중 끝무렵)에서 **세그폴트**로
  죽는다 — 2회 시도 2회 모두. 죽기 전까지 찍힌 압축률은 4.6~7.2배이므로 성공했다면
  지오메트리가 ~10MB 로 내려가 총 25MiB 안팎이었을 것이다. **추정이지 실측이 아니다.**
  그리고 Draco 산출은 런타임에 `DRACOLoader` + wasm 디코더를 요구하므로 **자산만으로는
  못 쓴다**(자기완결은 `vendor/` 직서빙으로 지킬 수 있으나 그것은 설계 분기다).

## 이 회차에 자산을 커밋하지 않은 이유

위임 상한이 **50MB** 였고 가장 작은 변형이 **76.32 MiB** 다. 그래서 `frontend/assets/`
에 아무것도 두지 않았다 — 절차와 게이트만 남긴다. 판정거리는 셋이고 전부 설계 분기다:

1. **어디까지 담을 것인가.** 컬렉션별 삼각형이 `Urban_Buildings` 733,948(70%) ·
   `Landmark_Manhattan_Bridge` 190,264(18%) 로 **둘이 88%** 다. 「먼 블록은 빼고
   갤러리 주변만」이 가장 큰 축이다.
2. **드로우콜.** 크기보다 이쪽이 먼저 막힐 수 있다 — 메시 노드가 **21,286개**다.
   재질별 병합(46개 이하)이면 바이트와 드로우콜이 **함께** 내려가지만, 그 순간
   컬렉션·오브젝트 단위 조작(작품 슬롯 12개·차량·간판)을 잃는다.
3. **Draco.** 로더 배선 + 디코더 vendoring + 이 환경의 인코더 세그폴트 회피.

## 2단계 — 인스턴싱 (감독 지시 2026-09-16 *"인스턴스 최대한 활용 가능할까."*)

통짜본이 큰 이유는 **같은 모양이 수천 벌 따로 저장돼 있어서**다. 실측하면 메시 19,251 종
중 실제 고유 형상은 **684 종**이다(H7 기준).

### 「같다」를 어떻게 정의했나 — 그리고 자릿수는 **고르지 않고 유도했다**

정의는 `mesh_hash.py` 한 곳이고 여섯 단계로 점점 느슨하게 잰다. 자릿수는 스윕해서
곡선이 평탄한 구간을 고른다(`CLAUDE.md`: *"유도할 수 있는 값이면 유도한다"*).

| 자릿수 | H1 raw | H2 norm | H5 raw+uv+mat | H7 raw+full | H6 norm+full |
|---:|---:|---:|---:|---:|---:|
| 2 | 510 | 232 | 678 | 679 | 616 |
| 3 | 516 | 237 | 690 | 690 | 639 |
| **4** | **516** | 242 | **679** | **679** | **628** |
| **5** | 521 | 245 | 684 | 684 | **628** |
| 6 | 557 | 262 | 733 | 733 | 659 |
| 7 | 644 | 268 | 809 | 809 | 726 |
| 8 | 659 | 291 | 829 | 829 | 770 |

**d=4~5 가 평탄 구간**이다(H6 은 628 로 **정확히 동일**, H7 은 ±0.7%). d≥6 부터 단조
증가하는데 그것은 부동소수 노이즈를 형상 차이로 세기 시작하는 지점이다. **d=5 를 쓴다** —
정규화 좌표에서 1e-5 이고 180m 로 환산하면 1.8mm, 원좌표에서는 0.01mm 다.

⚠ **H6 = H4 이고 H7 = H5 다** — 셰이딩(면 `use_smooth` + sharp edge)을 해시에 넣어도
그룹이 하나도 안 갈렸다. 즉 이 자산에서는 셰이딩이 형상과 함께 움직인다. **그래도 굽기
키는 H6/H7 만 허용한다** — 셰이딩 차이는 삼각형 수도 bbox 도 안 건드려서, 다음 자산에서
갈리기 시작하면 우리 검증 축 **어디에도 안 잡힌다.**

### 정규화는 **거의 이득이 없다** — 그래서 안 쓴다

| 축 | H7 무보정 | H6 정규화 |
|---|---:|---:|
| 그룹 | 684 | 628 |
| GLB mesh | 988 | 947 |
| 바이트(PNG) | 60,982,012 | 60,890,340 |
| 행렬 보정 | **불필요** | `W · T(c_M) · S(s_M/s_R) · T(−c_R)` |

**0.15% 차이다.** 정규화는 행렬을 고쳐 쓰는 만큼 위험을 지는데(비균등 스케일·법선), 그
대가로 얻는 것이 이것뿐이다. **`--key H7_raw_full`(기본값)이 권장**이고, 그쪽은
`object.data` 를 갈아끼우기만 해서 기하학적으로 무손실이다.

### shear 는 없다 — 그러나 **Y축 회전만 쓰는 계약은 못 쓴다**

* `matrix_world` 를 TRS 로 분해·재조립했을 때 1mm 넘게 움직이는 오브젝트 **0 / 21,052**.
  즉 shear 가 섞인 것이 없고, 정규화 경로도 안전하다.
* 교체 뒤 실제 변위(`geometryDriftM`)는 최대 **7.6e-06 m**(0.0076mm) — 임계의 1/131 이고
  float32 오차 수준이다. 1mm 초과 **0개**.
* **그러나 21,052 중 9,457개(44.9%)가 Y축 외 회전을 갖는다**(`Tactile_dome` 계열은
  upDot −1.0, 즉 뒤집혀 있다). 이것이 아래 ⑥의 핵심이다.

### 실측 — 통짜 vs 인스턴스

| **인스턴스 PNG** | **60,982,012 (58.16)** | 23,221,032 (22.15) | **988** | **21.54** | 21,313 | 21,286 | 1,322,096 | 동일 |
| 인스턴스 정규화 PNG | 60,890,340 (58.07) | 23,190,077 (22.12) | 947 | 22.47 | 21,313 | 21,286 | 1,322,096 | 동일 |

**「mesh 수만 24분의 1, 나머지는 전부 동일」이 「화면을 안 바꾸고 묶었다」의 축이다.**
정점은 1,907,224 → 1,192,315(−37%), 메시 데이터 삼각형은 1,300,484 → 835,514(−36%).
**씬 삼각형 1,322,096 은 불변** — 화면에 그려지는 것은 하나도 안 줄었다.

**`inst-rawwebp` 43.39 MiB 가 50MB 예산 아래로 들어오는 유일한 후보**이고, GitHub Pages 는
gzip 으로 보내므로 **실제 전송량은 7.43 MiB** 다(통짜 PNG 23.56 MiB 의 32%).

### 묶지 않은 것

* **모디파이어가 붙은 오브젝트 102개**(BEVEL 88 · WEIGHTED_NORMAL 88 · SOLIDIFY 14). 해시는
  메시 데이터만 보는데 `export_apply=True` 는 모디파이어를 **적용한** 결과를 내보내므로,
  같은 메시를 공유해도 화면이 달라진다. 전체의 0.5% 라 포기해도 손실이 없고, 반대로 묶으면
  그 위험이 **우리 검증 축 어디에도 안 잡힌다**(`bound_box` 조차 적용 전 값이라
  `geometryDriftM` 이 못 본다).
* 오브젝트 단위 재질 오버라이드는 **0개**였다(있으면 `data` 교체가 재질을 안 바꾼다).

### ⑥ 드로우콜 — 이 회차에 **줄지 않았다**

**glTF 의 mesh 공유는 드로우콜을 안 줄인다.** three 는 mesh 를 참조하는 노드마다 개별
`Mesh` 를 만든다 — 위 표에서 씬 Mesh 가 21,286 으로 **통짜와 같은** 것이 그 증거다. 줄어든
것은 바이트뿐이다.

줄이려면 런타임에서 같은 (geometry, material) 노드를 모아 `InstancedMesh` 로 바꾸는
후처리가 필요하다. **`frontend/js/world10/systems/instancing.ts` 의 `InstancePools` 를 그대로
쓸 수는 없다.** 읽어 보면 막는 것이 셋이다:

1. **`setTransform(x, y, z, ry, sx, sy, sz)` 이 Y축 회전 하나만 받는다.** 그 한계를
   `world10/export/import-glb.ts` 의 `decompose` 헤더가 적어 두었다 — *"블렌더에서 건물을
   기울이면 그 기울기는 버려진다."* 맨해튼은 **오브젝트의 44.9%(9,457개)가 Y축 외 회전**을
   갖는다. 그대로 쓰면 절반 가까이가 잘못 놓인다. 넓히려면 인스턴스 버퍼 레이아웃이
   바뀌고 그것은 world10 의 계약을 건드리는 일이다.
2. **사전 할당 슬롯 풀은 스트리밍 세계를 위한 설계다.** 부팅 중에만 `create`, 그 뒤
   `seal()`, 미사용 슬롯은 0 스케일, 반납은 swap-remove — 전부 파셀이 들고 나는 것을
   전제한다. 맨해튼은 **고정 세계 한 덩이**라 그 장치가 전부 불필요하고, 필요한 것은
   「한 번 만들어 채우고 끝」이다.
3. **`import * as THREE from 'three/webgpu'`** 라 청크가 갈린다(`vite.config.js:206-211`).
   월드11이 어느 빌드를 쓰는지가 먼저 정해져야 한다.

대안으로 glTF 에는 `EXT_mesh_gpu_instancing` 이 있고 three 의 `GLTFLoader` 는 그것을
`InstancedMesh` 로 읽는다. 다만 이 저장소는 **내보내기 쪽에서 그것을 이미 기각했다** —
`world10/export/glb.ts` 헤더: *"그걸로 구우면 블렌더에서 안 열린다(임포터가 확장을 무시하고
인스턴스를 전부 원점에 겹쳐 놓는다)."* 읽기 전용으로 쓰는 것은 다른 판단이지만, 블렌더
왕복이 이 자산의 제작 경로라는 점은 같이 봐야 한다. **3단계(런타임) 판단거리이고 이
회차에서는 구현하지 않았다.**

## ⚠ exporter 는 **바이트 단위로 재현되지 않는다** (2026-09-16 실측 — 1단계 기록 정정)

같은 원본·같은 인자로 두 번 구워 비교했다:

* **구조는 완전히 결정적이다** — `accessors` · `meshes` · `nodes` JSON 이 **완전 일치**하고
  bufferView 길이열도 같다.
* **UV 데이터만 흔들린다** — `TEXCOORD_0` accessor **81 / 3,133** 에서 값이 갈리고, 최대
  차이는 **1.19e-07**, 즉 **float32 ULP 한 개**다(1024px 텍스처에서 0.0001 픽셀).
* 그래서 **`sha256` 은 재실행마다 달라진다.**

**이것이 1단계 테스트의 `sha256` 축에 뜻하는 것**: 그 축은 「커밋된 자산이 조용히 바뀌는
것」은 잡지만 **「원본에서 다시 구우면 같은 바이트가 나온다」는 보장하지 않는다.** 자산을
재생성하면 `EXPECTED` 를 다시 박아야 하고, 그것은 실패가 아니라 정상이다. 바이트가 아니라
**형상이 같은지**를 보려면 `accessors`/`meshes`/`nodes` JSON 과 씬 실측(노드·Mesh·삼각형·
bbox)을 비교해야 한다 — 그쪽은 결정적이다.

## 검증기가 실제로 잡은 것 — 이름의 **공백**

`verify-glb.mjs` 를 처음 돌렸을 때 `rewritten: ["Scene Collection"]` 1건이 나왔다.
블렌더의 마스터 컬렉션 이름에 **공백**이 있고, three 의 `sanitizeNodeName` 은 공백을
지우는 대신 `_` 로 **바꾼다**(`.` 은 지운다). `glb_names.py` 첫 판본이 `.` 만 봤으므로
그 1건이 통과했다.

이것이 「로드 **후** 이름에서 `.` 찾기」로는 못 잡히는 부류다 — 로더가 이미 고친 뒤라
언제나 0건이 나온다. 그래서 축을 **경계**로 옮겼다: GLB json 의 원 이름과 로드 후
이름을 대조해 「로더가 고쳐 쓴 이름 0개」를 본다. `tests/manhattan-glb.test.ts` 의
M1·M1b 가 그 검출력을 뮤테이션으로 못 박는다.

최종 실측(`verify-glb.mjs`, exit 0):


## 좌표계

blend 는 Z-up, glTF 는 Y-up. 변환은 `(x, y, z) → (x, z, −y)` 하나이고 **두 곳**이 그것을
쓴다 — GLB 지오메트리는 exporter 의 `export_yup`, 카메라·라이트 JSON 은 `extract.py` 의
`_YUP` 행렬. 실측으로 맞는 것을 확인했다:

```
원본 bbox(Z-up)  min [−90, −90, −2]    max [90, 90, 88.11]   크기 180 × 180 × 90.11
산출 bbox(Y-up)  min [−90, −2, −90]    max [90, 88.11, 90]   크기 180 × 90.11 × 180
```

`01_DISTRICT_180m` 카메라: blend `[212, −240, 185]` → JSON `position [212, 185, 240]`.

## 남겨 둔 물음 (이 회차에서 판정하지 않음)

* **간판 문자열의 법무 축.** FONT 오브젝트 95개의 내용은 전부 **가상 상호**다
  (`WEST SIDE STUDIO` · `MANHATTAN ATELIER` · `RIVER COFFEE` · `CITY ARCHIVE` ·
  `HUDSON EDITIONS`). 다만 `TAXI` · `NYC` 로 표시된 노란 차량과 도어 roundel 은 실존
  택시의 트레이드드레스와 겹칠 여지가 있다 — 라이브 승격 전 §6 판단거리다.
**Node 에서 못 재는 것 하나**: `EXT_texture_webp` 가 `extensionsRequired` 에 들어간 자산은
`verify-glb.mjs` 가 **씬 축을 건너뛴다**(종료코드 **4**). three 의 WebP 확장이
`detectSupport()` 에서 `new Image()` 를 만드는데(`GLTFLoader.js:1493`) Node 에 그것이 없고,
required 확장이라 폴백도 없다. 건너뛴 사실은 결과 JSON 의 `loaderSkipped` 와 `notMeasured`
에 실린다 — **조용히 통과시키지 않는다.** WEBP 본의 씬 축은 브라우저에서만 잴 수 있고,
대신 PNG 본과 `accessors`/`meshes`/`nodes` JSON 이 **완전 동일**하다는 것을 실측했다(이미지만
다르다).

**확인된 것(더 이상 물음이 아니다)**: 원본 blend 의 이미지 메타에는 만든 사람의 로컬
경로가 남아 있다(`C:/Users/USER/Documents/Codex/…`). 산출 GLB 의 JSON 을 훑어 실측한
결과 그 문자열은 **0건**이다 — `images[]` 에 남는 키는 `bufferView` · `mimeType` ·
`name` 셋뿐이다. 즉 경로는 blend 안에만 있고 배포물로 새지 않는다.
