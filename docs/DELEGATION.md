# 위임 공통 조항 — 서브에이전트 프롬프트에 반드시 넣는 것

부팀장이 executor·검수관·디자이너에게 일을 넘길 때 **매번 손으로 조항을 쓰다가 빠뜨렸다.**
그래서 목록으로 고정한다. 위임 프롬프트를 쓸 때 이 파일을 먼저 열고, 해당 유형의 블록을
그대로 복사한 뒤 과제별 내용을 덧붙인다.

> **왜 이 파일이 생겼나 (2026-07-30)**
> 감독: *"지금보니 너 동작할때 자꾸 빠뜨리고. 실패하고."*
> 실측해보니 그날 위임 실패의 형태가 **조항 누락**이었다. 가장 비쌌던 것: executor 에게
> KST 구현을 넘길 때 *"테스트를 느슨하게 만들지 말 것"* 을 안 적었다. executor 는 실제
> 산술 단언을 전부 지우고 `null` 기대로 바꿔 CI 를 통과시켰고, 검수관이 **반려**했다
> (블로커 4건). 재작업에 리뷰 9분 + 재구현이 들었다. 조항 한 줄이 없어서다.
>
> 규율은 문서로 늘려도 안 지켜진다(CLAUDE.md 는 이미 17,756자다). 이 파일이 다른 이유는
> **쓰는 순간에 열는 체크리스트**라서다 — 기억에 의존하지 않는다.

> **누구를 부를지 이전에 — 부를 필요가 있는지부터 (2026-08-05, #195)**
> 배포 전 독립 스모크(B·executor)와 검수관(E)을 **매번** 부르는 것이 기본값이었다. 지금은
> **등급이 정한다**: `node scripts/verification-tier.mjs --base origin/main`.
> 등급표와 판정 규칙은 [`scripts/lib/verification-tier.mjs`](../scripts/lib/verification-tier.mjs)
> 한 곳이고 여기에 다시 적지 않는다. 판정 불가는 **가장 무거운 등급**이므로, 등급이 안
> 나오면 전부 부르는 쪽이 기본값이다. 근거는 `OPERATING-PRINCIPLES.md` §10-3.

## A. 모든 위임에 공통 (유형 무관)

```
## 절대 규칙
- **저장소 파일을 수정하지 않는다.**(조사·리뷰 유형) / **커밋하지 않는다.**(구현 유형)
  대조군 비교가 필요하면 `/tmp` 별도 클론을 쓰고 작업 후 삭제한다.
- **미커밋 파일을 삭제하지 않는다.** "스크래치 임시 파일 정리" 는 세션 스크래치패드에만
  적용된다 — 저장소 파일은 대상이 아니다.
- `git checkout <commit> -- <path>` 로 되돌린 뒤 복구하지 않으면 **이후 모든 측정이 옛
  코드를 잰 것**이 된다. 브랜치 전환도 금지.
- 보고 마지막에 `git status --short --untracked-files=all` 출력을 **그대로** 붙인다.
- 보고는 **한국어**. 사고과정도 한국어.

## 게시판 (docs/BOARD.md)
- **착수 전에 읽어라** — 「지금 유효한 지시」 전체와 「올라온 것」 최근 5건. 내 작업과
  충돌하는 지시가 있으면 **멈추고 상신한다**(임의로 해석해 진행하지 않는다).
- 보고 끝에 **「게시판에 올릴 것」** 을 적어라. 다음 사람이 알아야 할 관측·이슈·건의를
  `### YYYY-MM-DD · 직무 — 제목` 형식으로. **없으면 "없음" 이라고 적는다**(비워두지 마라).
- 파일을 직접 고치지는 마라. 반영은 위임자가 한다(동시 편집 충돌 방지).
- **사실오류를 넣지 마라.** 파일 성격을 적을 때는 `git ls-files` / `git check-ignore` 로
  실측하고 그 출력을 근거로 붙인다.
- **못 잰 것을 통과로 적지 마라.** 측정이 실패했으면 "무엇이 막았는지" 를 쓴다. 추측으로
  메우거나 재지 못한 항목을 조용히 생략하지 않는다.
```

**받은 보고를 검증하는 것은 위임자의 책임이다.** `git status` 가 clean 이라는 보고는
무결성의 증거가 아니다 — 지워서 clean 일 수도 있다. 위임 전에 내가 아는 미커밋 파일을
적어두고, 보고의 clean 을 그것과 대조한 뒤에만 통과시킨다.
그리고 **커밋 메시지에 "권고 반영" 을 적기 전에 `git diff` 로 실제 반영을 확인한다** —
보고를 검증 없이 옮겨 적은 적이 있다.

## B. 구현을 넘길 때 (executor)

A + 아래.

```
## 테스트를 느슨하게 만들지 마라
- 기존 테스트의 **단언을 약화시켜 통과시키는 것은 금지**다. 실제 값을 단언하던 것을
  null/undefined 기대로 바꾸거나, 범위를 넓히거나, 검사를 지우지 마라.
- 구현 때문에 기존 테스트가 깨지면 **그것이 신호다.** 테스트를 고치기 전에 "구현이 틀린
  것은 아닌가" 를 먼저 보고, 테스트를 고쳐야 한다면 **왜 옛 단언이 더는 유효하지 않은지**
  를 보고에 적어라.
- 새 코드 경로를 만들었으면 그 경로를 **실제로 실행하는** 테스트를 붙여라. 픽스처를 전부
  "없음/실패" 로만 채우면 정상 경로가 한 번도 안 돌고, 그것은 검증이 아니다.

## 게이트
- `npm run gate` 하나로 돌린다. 게이트를 손으로 조립하지 마라 —
  `;` 나열도, `set -e` + 파이프도 종료코드를 삼킨 전례가 있다.
- 통과하지 않으면 커밋이 pre-commit 훅에 막힌다. 우회(`--no-verify`)하지 마라.
```

### B-1. 별도 클론에서 돌리게 할 때 (대조군 실험·격리 실행)

> **왜 이 조항이 생겼나 (2026-08-05)**
> 검수관 게이트 명세 G4(대조군 스모크 N=5×2)를 executor 에게 넘기며 *"`npm ci` 또는
> `npm install` 이 **필요하면** 하라"* 고 **조건부**로 적었다. executor 는 안 했고,
> **10회 전부** 이렇게 즉시 실패했다:
>
> ```
> [*] FAIL  _site 조립   조립 실패(vite) — ./node_modules/.bin/vite: No such file or directory
> ```
>
> 로그가 926바이트(정상 2,500+)이고 다섯 개가 **같은 초에** 끝난 것으로 발견했다.
> 원인은 executor 의 판단 실패가 아니라 **반드시 해야 하는 일을 선택지로 준 것**이다.
> 조건부로 적으면 "필요한가?" 가 판단거리가 되고, 그 판단이 틀릴 자리가 생긴다.
>
> 그리고 **실패가 조용했다** — 스모크는 exit 1 로 정직하게 죽었는데, 위임 보고에는
> "완료" 로 올라왔다. 산출물 크기·종료 시각 같은 **싸구려 무결성 신호**를 확인 항목에
> 넣지 않으면 이 형태는 또 지나간다.

```
## 클론 준비 — 조건부로 적지 마라. 아래를 그대로 실행하고 결과를 보고하라
- 클론마다 의존성을 **반드시** 설치한다. 원본 `node_modules` 를 심볼릭 링크하지 마라
  (실행 경로가 원본을 가리켜 격리가 깨진다). **복사**하거나 `npm ci` 를 돌린다.
- 실행 **전에** 진입점이 실재하는지 확인하고 그 출력을 보고에 넣어라:
      ls <클론>/node_modules/.bin/vite
  없으면 거기서 멈추고 보고하라. 없는 채로 돌리면 전 회차가 무효다.

## 회차 실행 — 무결성 신호를 함께 남겨라
- 각 회차를 파일로 리다이렉트하고 `echo "EXIT=$?"` 를 덧붙인다(파이프 금지 — 진행이
  안 보여 "멈췄다"로 오판한 전례가 있다).
- 보고에 **회차별 로그 파일 크기와 종료 시각**을 붙여라. 크기가 비정상적으로 작거나
  여러 회차가 같은 초에 끝났으면 **그 자체가 실패 신호**다 — "완료" 로 적지 마라.
- 회차 수를 줄였으면 **줄인 사실과 이유**를 보고에 적어라. 명세대로 돌린 것처럼 적지 마라.
```

## C. 뮤테이션을 넘길 때

A + B + 아래.

```
## 뮤테이션 절차
각 건: **적용 → 테스트 → 결과 기록 → 즉시 되돌리기.** 되돌리기를 빠뜨리면 이후 모든
측정이 오염된다. 되돌린 뒤 `git diff --stat -- <path>` 가 비었음을 보고에 붙여라.

## 금지 표현
- **"구조 설계로 방어됨"** 같은 말을 쓰지 마라. 그것은 테스트가 깨졌다는 증거가 아니다.
- 뮤테이션을 적용할 수 없었으면 **"적용 불가 — 이유"**.
- 적용은 됐는데 안 깨졌으면 **"적용됨 · 안 깨짐"**. 이 둘은 완전히 다른 결과다.
- 어느 테스트가 깨졌는지 **이름을 적어라**. 개수만으로는 검출력을 판정할 수 없다.

## 기대와 다른 결과가 나오면
그것을 보고 맨 앞에 요약해라. 그게 이 작업의 산출물이다. 다만 **원인을 단정하지 마라** —
"안 깨졌다" 는 관측이고 "테스트가 없다" 는 해석이다. 같은 파일의 다른 뮤테이션이 깨졌다면
두 해석은 모순이므로 위임자가 판정한다.
```

> 실제 사고: executor 가 `Math.max(1, months)` 제거가 안 깨진 것을 보고 *"payroll 산술이
> CI 에서 실행되지 않는다"* 고 결론했다. 실측하니 그 줄은 **도달 불가 방어 코드**였고
> (정렬로 `months >= 1` 이 보장된다) 같은 파일의 다른 뮤테이션은 깨졌다. 관측은 맞았고
> 해석이 틀렸다.

## E. 검수관을 부를 때 (§10-4)

무조건 트리거: `.github/workflows/**` · `scripts/smoke/**` diff.
그 외에 보안 경계·라이브 런타임·**반려 이력이 있는 브랜치**도 부른다.

```
- 리뷰 범위를 **커밋 해시로** 준다(`git diff A..B`). 폐기된 WIP 커밋이 중간에 있으면
  그것을 명시한다.
- 내 주장을 **검증 가능한 형태**로 적는다: "X 를 했다" 가 아니라 "X 를 했고, 근거는
  이 명령의 이 출력이다. 이것이 성립하는지 봐 달라".
- 판정을 요구한다: **승인 / 조건부 승인 / 반려**. 블로커와 비블로커 권고를 분리.
- 내가 아직 확인 못 한 것을 숨기지 않고 "이건 당신이 봐 달라" 고 명시한다.
```

**판정을 받은 뒤** — 반려는 병합 금지, 조건부 승인은 **재확인 후** 병합(내가 "해소했다" 고
판단하는 것으로 갈음하지 않는다). 절차 전문은
[.claude/agents/release-reviewer.md](../.claude/agents/release-reviewer.md) 의 "반려의 구속력"
한 곳이다 — 여기에 다시 적지 않는다.

## F. 화면 판정을 넘길 때 (스크린샷·시각 확인)

A + 아래.

```
## 무엇을 재는지 정확히 적어라 — 비율만 묻지 마라
- "X 가 화면에 보이는가" 는 **X 가 화면 어딘가에 있는가**만 잰다. 의도가 "가까이 있다"·
  "정면에 있다"·"크게 보인다" 라면 그 축을 **따로** 물어라.
  · 거리: "카메라에서 X 까지 최단거리 N m 이내인가"
  · 화면상 위치: "화면 하단 1/3 에 있는가"(가까운 것은 아래로 온다)
  · 크기: "화면 세로의 몇 %를 차지하는가"
- 판정 근거는 수치로. 다만 **수치가 통과했다고 의도가 달성된 것은 아니다** — 애매하면
  "수치는 통과했으나 의도 달성은 확신 못 함" 이라고 적어라. 그러면 위임자가 화면을 본다.
```

> 실제 사고(2026-08-04): `?at=river` 스폰 판정에서 *"물 픽셀 13.44% · 화면 중단부"* 로 PASS
> 가 났다. 화면을 직접 보니 그 물은 **수평선 너머 바다**였고 눈앞은 잔디와 도로였다. "물가에
> 선다" 는 의도가 전혀 달성되지 않았는데 수치는 전부 초록이었다. **executor 가 아니라 위임자가
> 준 기준이 틀렸다** — 비율은 거리를 재지 않는다.
