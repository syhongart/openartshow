## 실측 용량 (성능 전문가 · 코드 기반 계산, 가정치 명시)

| **TURN 대역폭 비용** | 게스트-시간당 ≈0.178GB → $0.07~0.15. 월 1천h→$71~142, 1만h→$712~1,424 | 데이터채널만(A/V 없음). 관리형 $0.4~0.8/GB 가정. 동시접속·NAT실패율 측정불가 |
| **Pages 100GB/월 초과** | 월 약 7,700~9,900 세션(하루 260~330) | 세션 ≈13MB 실측(하늘 텍스처 3장=5.59MB=43%). 재방문·캐시 미반영 상한 |
| **영속화** | 저장용량은 병목 아님(수 MB), 병목은 쓰기 QPS | localStorage→서버 포트 시 addDwell 2초 간격. 실측 텔레메트리 없음(추정) |

## 현 구조 한 줄 요약
정적 사이트(GitHub Pages+CDN) + **P2P 호스트릴레이 멀티(PeerJS 공용 브로커)** +
**localStorage 영속화(=사실상 공유 상태 없음)**. 읽기(감상)는 잘 확장, **실시간·영속화는 미확장**.

## 3단계 이전 경로

> ⚠ **「N단계」의 SSOT 는 이 절이다** (2026-08-16 정리). 저장소에 **단계 사다리가 셋** 있고
> **같은 번호가 서로 다른 것을 가리킨다** — `REFERENCES.md` 의 「백엔드 진화 로드맵」,
> `OPENWORLD.md` 의 「5단계 로드맵」. 감독이 *"1단계부터 하자"* 고 말하는 순간 **세 개의
> 다른 작업이 시작될 수 있다.**
>
> 그래서 **인프라 확장(호스팅·시그널링·영속화)을 말할 때의 단계는 여기 것**이고,
> 다른 두 문서의 번호는 각자 문서 안에서만 유효하다(그쪽에도 같은 경고를 달았다).
> 세 사다리를 하나로 합치는 것은 별도 결정 사안이라 **지금은 「어느 사다리인지 밝히는
> 것」까지만** 한다 — 번호를 임의로 다시 매기면 세 문서를 인용한 태스크·게시판 기록이
> 전부 낡는다.

### 0단계 — 지금(트래픽 없음): 그대로 둔다
- 현 구조로 충분. 조기 서버화는 그 자체가 실패(운영비·복잡도).
- 유일한 상시 관리: 정적 자산 용량(첫 로드 체감) 절제.

### 1단계 — 정적 호스팅 이전 (트리거: Pages 대역폭 경고 / 로딩 지연 민원)
- **무엇**: GitHub Pages → Cloudflare Pages / Netlify / S3+CloudFront.
- **왜**: 정적 사이트라 이전이 거의 무위험. Pages 무료 ~100GB/월 소프트리밋 회피 + 글로벌 CDN.
- **난이도/기간**: 낮음 · 반나절~1일. 배포 파이프라인(deploy.yml) 타깃만 교체.
- **비용**: 무료 티어~월 수 달러대.

### 2단계 — 시그널링 자체 호스팅 + TURN (트리거: 동시 접속 방 증가 / 접속 실패 민원)
- **무엇**: PeerJS 공용 브로커(0.peerjs.com) → **자체 PeerServer**(소형 VM/컨테이너) +
  **TURN 서버**(coturn 자체호스팅 or 관리형 Twilio/Metered).
- **왜**: ①공용 브로커는 프로덕션 불가(레이트리밋·무SLA) ②TURN 없으면 대칭 NAT 뒤 일부 접속 실패.
  코드는 이미 `window.LU_PEER_OPTS` 오버라이드 훅이 있어 **한 줄 설정으로 전환** 가능(재작성 0).
- **중요 원칙**: 방을 키우지 않는다. 호스트릴레이는 방 하나가 물리적 천장(성능표 N값 참조).
  스케일은 **작은 방 수천 개로 샤딩** — 우리 "작가별 갤러리" 모델과 정확히 일치.
- **난이도/기간**: 중 · 2~4일(서버 프로비저닝·TLS·모니터링 포함).
- **비용**: PeerServer 소형 VM 월 5~10달러대 + TURN은 **중계 대역폭 종량**(성능표 비용 참조).

### 3단계 — 영속화 백엔드 (트리거: "여러 사람이 공유하는 기록"이 제품 가치가 되는 순간)
- **무엇**: DB + API + 인증. 방명록·프로필·아바타·방문통계·(AI평)를 **서버 공유 상태**로.
- **왜**: 현재 localStorage는 브라우저 로컬 → 10만 명의 방명록이 서로 안 보임(공유의 착시).
  BACKLOG "방명록 백엔드(영속화)"가 AI 관람객 로드맵의 **선행조건**으로 이미 명시됨.
- **백엔드 후보 비교**:
  | 후보 | 성격 | 장점 | 유의 |
  |---|---|---|---|
  | **Supabase** | 관리형 Postgres+Auth+RLS | SQL·행수준보안·무료티어 후함, 관계형에 강함 | 셀프호스팅도 가능(락인 완화) |
  | **Firebase** | 관리형 실시간 NoSQL+Auth | 실시간 구독·모바일 SDK 성숙 | 쿼리 제약·비용 예측 어려움·구글 락인 |
  | **자체 API**(Node+PG) | 직접 구축 | 완전 통제·이식성 | 개발·운영 비용 최대, 초기 과함 |
  - **권고**: 초기엔 **Supabase**(관계형·인증·RLS·무료티어) — 정식 오픈 규모에 적정, 나중에 자체 API로 이관 여지.
- **난이도/기간**: 높음 · 1~2주+(스키마·인증·마이그레이션·기존 localStorage 병합).
- **개인정보/약관 연동**: 서버가 개인 데이터를 보관하는 순간 §6 법무 게이트(개인정보처리방침) **필수 선행**.

## "정식 오픈 게이트"에 반드시 넣을 2가지 (미룰 수 없음)
- **2단계(시그널링+TURN)**: 실시간이 제품 핵심이면 공용 브로커론 못 연다.
- **3단계(영속화 백엔드)**: 소셜·AI평이 남으려면 필수. 법무(개인정보)와 짝.
- 1단계(정적 이전)는 대역폭 물리는 시점에 즉시 — 항상 반나절 카드로 대기.
