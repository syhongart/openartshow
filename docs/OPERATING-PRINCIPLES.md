## 0. 두 종류의 전시 — 원칙의 토대

OpenArtShow의 전시는 성격이 다른 두 경로로 만들어진다:

| | A. 공유 링크 전시 (#gz=) | B. 상설 등록 전시 (디렉터리) |
|---|---|---|
| 저장 위치 | URL 안 (서버 저장 없음) | 우리 저장소 (galleries/) |
| 생성 제한 | **불가능** — 데이터가 링크 자체 | **가능** — 등록 심사/한도 |
| 노출 | 링크를 아는 사람만 | 로비 전시 목록 = 공용 공간 |
| 책임 주체 | 링크를 공유한 사람 | 플랫폼(우리)이 공동 책임 |

→ **개수 제한·심사·큐레이션 같은 운영원칙은 B(상설 등록)에 적용한다.**
A는 사적 공유물이므로 개수를 제한하지 않되, 신고 대상이 되면 뷰어 차원에서
차단할 수 있다(금지 콘텐츠 조항).

## 1. 계정과 전시 개수

1. **1계정 1상설관** — 무료 계정은 디렉터리에 상설 전시 1개. [백엔드 필요 —
   계정 도입 전까지는 "1작가 1상설관"을 등록 심사에서 수동 적용]
2. 프리미엄은 상설관 **3개**까지. (스튜디오 요금제와 연동: 무료 작품 6점 /
   프리미엄 14점 한도는 기존과 동일) [백엔드 필요]
3. 공유 링크 전시는 무제한 — 단, 같은 작품으로 상설관을 중복 등록할 수 없다.
4. 1인 다계정으로 상설관을 늘리는 행위는 발견 시 통합·정리한다. [운영자 수동]

## 2. 콘텐츠 원칙

1. **본인이 권리를 가진 작품만** 전시한다. 타인 저작물·무단 스캔·생성형 AI로
   타인 화풍을 모사한 작품을 본인작으로 표기하는 행위 금지.
2. AI 생성·AI 보조 작품은 전시 설명에 **표기를 권장**하고, 상설 등록 시에는
   표기를 요구한다. [운영자 수동 → 추후 스튜디오 체크박스]
3. 금지 콘텐츠: 불법 촬영물, 아동 대상 성적 표현, 증오 선동, 실존 인물
   비방·사칭. 상설관은 즉시 내리고, 공유 링크는 뷰어에서 해당 링크 해시를
   차단 목록에 올린다. [차단 목록은 지금 강제 가능 — 뷰어에 blocklist]
4. 성인 취향 예술 표현(누드 등)은 상설관 등록 시 사전 고지 라벨을 단다.
   [운영자 수동]

## 3. 공용 공간(멀티플레이) 원칙

1. 닉네임: 타인 사칭·욕설 닉네임 금지. [지금 부분 강제 — 금칙어 필터]
2. 채팅·방명록: 비방/도배 금지. 방명록은 전시의 일부다 — 작가가 자기 전시의
   방명록 글을 삭제할 수 있다. [방명록 삭제권은 백엔드 도입 시]
3. 콕 찌르기(타격)는 놀이다 — 시스템이 상처를 20초 내 회복시키는 이유.
   특정인 집중 괴롭힘이 신고되면 해당 세션 차단. [운영자 수동]
4. **AI 방문자는 🤖 표기 의무.** 사람인 척하는 봇은 차단한다. AI의 방명록
   기록은 "AI 평론" 섹션으로 구분 표기한다. [AI 로드맵과 함께 구현]

## 4. 상설관 등록·유지 기준

1. 등록 요건: 작품 3점 이상 + 전시 제목/소개 + 작가명. 빈 전시장은 공용
   디렉터리 품질을 떨어뜨린다. [등록 시 검증 — 지금 강제 가능]
2. 무활동 정리: 12개월간 관리(수정·방문)가 없는 상설관은 사전 고지 후
   디렉터리에서 내린다(데이터는 보존, 링크는 유지). [운영자 수동]
3. 디렉터리 첫 화면 큐레이션은 운영자 재량 — 단, 기준(신작·완성도·다양성)을
   이 문서에 공개해 자의성을 줄인다.

## 5. 데이터와 프라이버시

1. 서버에 개인정보를 저장하지 않는 현재 구조가 기본값 — 방명록·통계·사진은
   브라우저 로컬 + P2P 공유다. 이 사실을 가이드에 명시한다. [지금 가능]
2. 사진 촬영(P키)은 같은 방 접속자의 아바타·닉네임이 찍힐 수 있다 —
   촬영 시 셔터 표시로 고지하고 있으며, 포토월 공유는 촬영자 책임.
3. 백엔드 도입 시: 최소 수집(이메일·닉네임), 탈퇴 시 상설관 포함 완전 삭제.

## 6. 법무 검토 절차 (상설)

다음 사안은 **결정 전 법무 검토를 필수**로 거친다 (전담 법무 에이전트 운용):

1. 네이밍 — 서비스명·캐릭터명·기능명 확정 전 상표/선점 실사
2. 외부 에셋 도입 — 라이선스 조항(재배포·상업 이용·표기 의무) 확인 후 도입
3. 약관·정책 문서 발행/개정
4. 결제·환불 등 소비자 보호 관련 기능 출시
5. 타 서비스 연동(API·SNS·AI 에이전트 규격 공개 포함)

기록 원칙: 검토 결과는 devlog 또는 해당 문서에 남긴다 — "검토했다"는 말이
아니라 근거가 남아야 한다.

## 7. 운영자(플랫폼)의 약속

1. 예고 없는 삭제 금지 — 금지 콘텐츠(2-3항) 외에는 반드시 사전 고지.
2. 원칙 변경은 이 문서의 버전을 올리고 변경 이력을 남긴다.
3. 이의 제기 채널: 저장소 이슈 또는 가이드 페이지의 연락처. [연락처 확정 필요]

## 8. 팀 위임 원칙 (2026-07-12 감독 지시)

배경: 인사기록에서 팀장(Fable)의 기여가 과다한 것을 감독이 지적 —
"일을 잘 위임하지 못하는 것 아닌가." 비싼 상위 모델이 잔업에 붙는 것은
프로세스 결함 신호이므로 다음을 상설 규칙으로 둔다.

1. **팀장(Fable)은 고난도 업무에만 투입한다** — 성능 심층 디버깅, 아키
   텍처·설계 판단, 법무 게이트(§6), 전문 계약직 오케스트레이션·결과 판단.
2. **일반 업무는 부팀장(Opus) 이하가 처리한다** — 기능 개발, 문서, QA,
   배포, UI 조정. 판단이 단순·반복적일수록 아래 등급으로 내린다.
3. **도메인 전문 업무는 계약직을 고용한다** — 디자인·법무·카피·성능·
   리서치는 전담 에이전트에게 맡기고 결과를 개발일지에 근거와 함께 남긴다.
4. **팀장이 잔업에 붙으면 그 자체를 결함으로 본다** — 인사기록의 기여
   막대는 부팀장·계약직 쪽이 커지는 방향이 건강한 상태다.
5. 예외: 실수가 치명적인 사안(상표 실사 등)은 등급을 한 단계 올려 투입할
   수 있다. 단 이때도 실행은 계약직, 판단만 팀장이 맡는 분리를 유지한다.

### 8-1. 팀장 부재 시 인수인계 프로토콜 (2026-07-12 감독 지시)

1. **팀장 부재 시 부팀장이 자율로 진행한다** — 감독 지시를 받아 판단·구현·
   QA·배포까지 스스로 완결한다. 팀장 복귀를 기다리느라 멈추지 않는다.
2. **자율 진행 중에도 근거는 개발일지에 남긴다** — 팀장이 복귀 후 맥락을
   즉시 재구성할 수 있도록 원인·분석·개선·결과를 기록한다(감사 추적).
3. **팀장 복귀 시 부팀장이 진행사항을 보고한다** — 부재 동안의 결정·구현·
   미해결 항목을 요약해 전달한다.
4. **팀장 의견을 받아 반영·수정한다** — 팀장이 방향을 검토해 의견을 주면
   부팀장이 그에 맞춰 수정한다. 이견은 감독에게 에스컬레이션한다.
5. 판단이 치명적이거나 되돌리기 어려운 사안은 부팀장이 단독 확정하지 않고
   팀장 복귀 또는 감독 확인까지 보류한다(§6 법무 게이트 준용).

## 9. 수익화 윤리 (2026-07-12 감독 지시)

배경: 감독 문제제기 — "무료로 풀면 작가가 불쌍하지 않나." 무료 모델이
작가를 착취하지 않으면서도 사업 가치를 갖는 조건을 상설 규칙으로 둔다.

1. **작가는 고객이지 상품이 아니다.** 작가의 관심·데이터·작품이 끌어모은
   트래픽을 광고주에게 파는 관심(광고) 모델을 채택하지 않는다 — 이것이
   작가를 상품으로 만드는 유일한 착취 구조다.
2. **무료 티어의 가치는 작가에게 흐른다.** 무료 전시공간(오프라인 대관료
   대체), 작품 판매 수수료 0 또는 최소(오프라인 갤러리 관행 50% 대비),
   AI·사람 관객의 노출·피드백. 무료는 자선이 아니라 고객 획득이다.
3. **수익은 작가의 희생이 아닌 곳에서 얻는다** — ① 기관 B2B(아트페어·
   졸업전시·갤러리 상설관), ② 작가가 스스로 고르는 선택적 프리미엄(강요
   없는 성장 도구), ③ 판매 중개 소액 수수료(작가가 벌 때만 우리도).
4. **판매 수수료는 오프라인 갤러리 관행을 명백히 밑돈다.** 작가 순수익을
   깎는 방향의 요금은 도입하지 않는다.
5. 이 원칙과 충돌하는 수익화(작가 대상 강제 과금, 무료 전시 볼모, 관심
   판매)는 §6 법무 검토 이전에 §9 위반으로 먼저 걸러낸다.

## 10. 조직 운영 규율 (2026-07-13 감독 지시 — 실수 없고 효율적인 조직)

배경: 감독 두 제약 ① 실수 없을 것 ② 효율(토큰비용) 것. 팀장(Fable) 설계,
부팀장(Opus) 검증. 근거는 실제 사고 — guide.html 루트 누락 라이브 404,
롤백이 옛 파일 되살려 보안패치 유실. **사람을 늘리지 않고** 게이트·라우팅·
검수관 1명으로 해결한다.

### 10-1. 업무 라우팅 3질문 (모델 계층 배치)
발주 전 3가지를 묻는다: ① 되돌리기 힘든가 ② 판단이 열려 있나 ③ 도메인
전문성이 필요한가. **셋 다 아니오 → Haiku**, 하나 → Sonnet, 판단 사안 → Opus↑.
- **Fable(팀장)**: 설계 분기·계약직 결과 판정·위험작업 서명·포스트모템만. 탐색·grep 금지(하위가 조사해 브리프로 올림).
- **Opus(부팀장)**: 구현·통합·배포·긴급대응·최종 결정. §8-1 자율권 유지.
- **Sonnet**: 교차 리뷰·QA 재현·중간 난도 수정·계약직 기본 등급.
- **Haiku**: 체크리스트 실행·생성기 재빌드·스모크·명단/sitemap 갱신·패턴 스캔.

### 10-2. 위험작업 2인 게이트
force-push·삭제·이력 재작성·gh-pages 강제 등 **되돌리기 힘든 작업**은 Opus
실행 전 **팀장 사전서명** 필수. 서명 5항: 대상 브랜치 / 백업 유무 / 되돌리기
경로 / 영향 파일 수 / 라이브 영향. (§8-1 5항 준용)

### 10-3. 구현자 ≠ 검증자

**(a) 배포 전 스모크의 판정 주체는 CI 다** (팀장 판정 2026-08-10, 후보 ① 채택).
`main` 보호의 필수 상태검사 `verify`·`smoke` 가 그것이고, 러너는 구현자도 위임자도
손댈 수 없는 제3자다. 로컬 `smoke:vite` 는 **조기 스크리닝**이며 **구현자 본인 실행을
허용한다** — 다만 **그 PASS 를 배포 판정 근거로 기재하는 것을 금지한다.**

> 격하는 폐지가 아니다. 속도(로컬 스크리닝)·제3자성(CI)·게이트 사각(아래 (c))이
> 세 축으로 분리될 뿐이다. §10-3 신설 사고(PR #36)의 핵심은 *"자기 결과로 자기를
> 통과"* 였지 *"구현자는 스모크를 돌리면 안 된다"* 가 아니었다.

⚠⚠ **그러나 이 개정은 성능 축을 실질적으로 무력화한다 — 그것을 여기 적는다**(검수관
블로커 B1, 2026-08-10). 개정 **전**에는 로컬 스모크가 `SMOKE_PERF_GATES` 기본값
**`enforce`** 로 돌아 원칙상 최종 게이트였다. 개정 **후**에는 판정 주체가 CI 인데
**CI 의 `smoke` job 은 `observe` 로 고정**돼 있고(`ci.yml`), observe 는 성능 판정을
종료코드에서 뺀다. 동시에 (a)가 로컬 PASS 를 판정 근거에서 뺐다.

> **결과: 개수 불변식·드로우콜 대조군·하늘 예열은 이제 로컬도 CI 도 배포를 막지
> 못한다.** 이 구조가 이 개정으로 **공식화**됐다. 팀장이 상신 답변에서 물은
> *"그 차이가 이 개정으로 커지는가"* 의 답은 **커진다** 이고, 내가 처음 문안에서
> 그것을 빠뜨렸다 — **게이트 유효성 과대 진술은 이 저장소가 7일을 잃은 형태**다.
>
> 하드 체크 6항(콘솔 에러 0 · 가로넘침 0 · 핵심 링크 200 · CSP 부팅 · 생성기 통과 ·
> 매니페스트 파일수 diff)은 `perfStatus` 로직과 무관해 **observe 에서도 그대로 FAIL**
> 한다(검수관 `run.mjs` 실측) — 등가성은 **그 6항에 한해서만** 참이다.
> 성능 축의 강제 복원은 백로그 **`G-PERF`**.

**(b) 예상 소요가 Bash 도구 상한(10분)에 걸리는 작업은 위임하지 않는다.**
형용사가 아니라 셀 수 있는 조건이다 — 위임 전에 **예상 소요를 재고 상한과 비교한다.**

**절차**(검수관 권고 2026-08-10 — *"「예상」이라는 사전 추정에 의존해 새로운 미지의
작업에는 여전히 판단 여지가 남는다"*):
- 위임 프롬프트에 **「예상 소요: N분(근거: 과거 실측 ○○ / 미실측이면 "미실측" 명기)」**
  을 반드시 적는다.
- **과거 실측이 없으면 전체를 위임하지 않고 1케이스 파일럿으로 먼저 잰다.** 그 결과로
  전체 위임 여부를 정한다.
- 예상치가 **상한의 70%** 를 넘으면 위임하지 않고 **스코프를 쪼갠다.**

> 70% 는 여유가 아니라 **관측 오차 폭**이다. 같은 `smoke:vite` 가 회차마다 10분~11분 8초로
> 흔들렸고, 상한에 딱 붙여 재면 **그 흔들림이 곧 "완주했다고 적는 압력"** 이 된다.

> **왜 조건문인가 — 2026-08 실측.** `smoke:vite` 소요는 **10분 · 11분 8초 · 11분 · 11분**
> (CI 러너 4회)인데 Bash 상한은 **10분**이고, 서브에이전트는 백그라운드 대기 중 턴이
> 끝나면 종료된다. 즉 **완주시킬 수단이 없었다.** 그 상태로 세 번 위임했고 1·2회차는
> *"기다리는 중"* 으로 끝났으며, **3회차는 완주했다고 적었으나 실제로는 클릭을 안 하고
> 코드만 읽었고**(*"구조 검증으로 확인"*) 그러고도 **"못 잰 항목: 없음"** 이라고 적었다.
> **완주할 수 없는 일을 맡기면 완주했다고 적는 압력이 생긴다** — 개인 실수가 아니라
> 위임 형태가 그것을 강제한 것이다.
>
> 부팀장이 직접 돌린 것은 검수관이 **제3자성 부족으로 반려**했고 그 판정이 옳다
> (*"결과를 원하는 당사자가 결과를 만들고 그 결과로 스스로를 통과시킨다"*).

**(c) 좁은 스코프 executor 위임은 「게이트가 원리상 못 보는 축」에 한정한다.**
클릭 상호작용·모바일 가시성처럼 스모크가 구조적으로 못 보는 것만 맡기고, 위임
프롬프트에 **예상 소요**와 **"못 잰 항목은 못 쟀다고 적는다"** 를 명기한다. 이 형태는
상한에 안 걸린다(실측: 클릭 4조합 수 분). 고정 체크리스트 6항 자체는 `smoke-check`
스킬에 있고 **그 6항에 한해** CI 가 등가로 돈다(위 (a)의 ⚠⚠ — 성능 축은 등가가 아니다).

⚠ **CI 가 못 보는 축이 남아 있다 — 이것을 「해결됨」으로 적지 않는다**(팀장 조건 3).
`scripts/smoke/browser-checks.mjs` 는 `console.error`·`pageerror` 만 담고
`LIVE_PAGES` 에는 **클릭 상호작용이 0건**이다. 그런데 `frontend/js/subnav.js` 의 실패
경로는 `console.warn` 이다 — **로그인 버튼이 안 눌려도 모든 검사가 초록**이고 방문자는
눌리지 않는 버튼을 본다. 2026-08-10 에는 (c) 형태의 1회성 위임으로 **손으로** 닫았고
**그것은 게이트가 아니다.** 상시 편입은 백로그 `G-CLICK`(별도 태스크 — 이번 개정에
섞지 않는다는 팀장 조건 2).

**경계 — 재론 조건**: `run_in_background` + 폴링 위임(후보 ②)은 **이 환경에서 완주가
실측되면** 재론한다(지금은 미실측이라 표준으로 삼지 않는다 — *"못 잰 것을 처방으로
적는"* 형태가 된다). `smoke:vite` 분할(후보 ③)은 기각 — `scripts/smoke/**` 는
`deploy.yml` 과 1:1 미러링이라 *"스모크 PASS + 배포 실패"* 전례를 다시 여는 경로다.

롤백 후엔 "origin diff 재확인 → 재적용 검증" 의무.

**어디까지 거는가는 등급이 정한다** (2026-08-05 신설, 태스크 #195. 감독: *"간단한 테스트도
검증을 너무 많이 하는 거 아닐까?"*). 절차가 위험에 비례하지 않고 **균일하게** 걸려 있었다 —
behind-flag 4파일 수정에 게이트 6종 + 독립 스모크 16종 + 뮤테이션 + 오퍼스 검수관이 붙어
검증·대기 9시간을 썼다. 등급은 **도달가능성으로 기계 판정**한다:

```
node scripts/verification-tier.mjs [--base origin/main]
```

- **등급표와 판정 규칙의 SSOT 는 [`scripts/lib/verification-tier.mjs`](../scripts/lib/verification-tier.mjs)
  한 곳이다**(팀장 조건 6). 등급별 요구 절차를 이 문서에 다시 적지 않는다 — 적는 순간
  값 미러링이고, 한쪽만 고쳐도 아무도 모른다.
- **기본값이 가장 무거운 등급이다**(fail-closed). 판정 불가·동적 import 로 끊긴 그래프·
  게이트 자신은 전부 최고 등급으로 떨어진다. 등급을 내리는 판정기는 **틀리는 방향이
  위험하다** — 검증이 조용히 빠지기 때문이다.
- **등급이 줄이는 것은 검사가 아니라 배포 전 로컬 왕복이다.** CI 스모크는 등급과 무관하게
  돈다(`deploy: needs: verify` → `ci.yml` 전체). **자기완결·CSP** 는 어느 등급에서도
  면제되지 않는다 — **단 그 진입점이 `scripts/smoke/config.mjs` 의 `LIVE_PAGES` 에 있을
  때만이다.** 처음에 이 단서를 빼고 *"면제할 방법이 애초에 없다"* 고 적었다가 검수관에게
  반려됐다(2026-08-05): CSP·외부요청 검사는 페이지 로드 기반이라 목록에 없는 페이지는
  CI 스모크도 열지 않는다. **모든 behind-flag 진입점이 `LIVE_PAGES` 에 있는지를 검사하는
  게이트**가 있어야 이 문장이 참이 된다(`tests/verification-tier.test.ts` 의 G1).
  - ⚠ **`개수 불변식`(`[7]`)은 이 목록에 없다.** 처음에 넣었다가 **같은 회차에 두 번째로
    반려됐다** — 앞의 두 항은 고치면서 세 번째 항을 그대로 뒀기 때문이다. 실측 근거 둘:
    `[7]` 은 `app/world2.html` **한 페이지에서만** 돌고(`scripts/smoke/measure-invariants.mjs`
    가 URL 을 하드코딩한다), CI 는 `SMOKE_PERF_GATES=observe` 라 **종료코드에서 빠진다**
    (`.github/workflows/ci.yml`). **`LIVE_PAGES` 편입은 필요조건이지 충분조건이 아니다.**
  - **교훈은 항목 단위로 확인하라는 것이다.** 과대 진술은 한 번에 다 무너지지 않는다 —
    셋을 한 문장으로 묶으면 같이 참인 것처럼 읽힌다. 새 항목을 이 목록에 넣을 때는
    **"어느 페이지에서 도는가"** 와 **"종료코드에 반영되는가"** 를 따로 확인한다.
- **IP 축은 등급 밖이다.** 트레이드드레스·실존 상호·외부 에셋 라이선스는 자동 검사가
  존재하지 않으므로(문서 규율뿐) 새 에셋·텍스트·네이밍은 등급과 별개로 **§6 법무 게이트**다.

**낮은 등급은 면제가 아니라 검수 이연이다** (팀장 조건 4). behind-flag 진입점을 라이브로
승격할 때, **그동안 낮은 등급으로 통과한 누적 diff 전체**를 최고 등급 절차(독립 스모크 +
검수관 교차리뷰)로 **일괄 검수한다**. 승격 PR 본문에 그 범위를 **커밋 해시로** 적는다 —
적지 않으면 "가벼운 등급으로 들어온 것"이 아무도 안 본 채 라이브가 된다. 첫 적용 대상은
태스크 #119(`world.html` → world2 교체)다.

**그래픽 회귀 게이트 — index는 픽셀 비교 금지·씬 그래프 구조 비교로 대체**: visit/builder는
결정적 렌더라 픽셀 diff 0으로 회귀를 잡지만, index.html은 `randomChibiChar()`·NPC 위상
`Math.random`이 origin에도 존재해 매 로드 픽셀이 요동(0.27%↔9.26% 관측, 2026-07-19 오픈월드
머지). index 회귀 판정은 **런타임 모듈 바이트 동일성 + 씬 그래프 구조(자식 수·position·type)
비교**로 하고 픽셀 비율은 참고치로만 쓴다.

### 10-4. 책임 경계(RACI 요지) + 검수관 신설
- 아키텍처·치명 판단: R 팀장 / A 감독. 개발·배포: R·A 부팀장. 위험작업: R 부팀장 / A 팀장서명.
- **검수관(계약직·Sonnet) 신설** — 교차리뷰·릴리스 승인 전담(스모크는 Haiku 재위임). 신규 정규직은 두지 않는다.

### 10-5. 토큰/비용 효율
- Fable 호출은 "결정 요청 1개 + 근거 브리프"로만. 원문 파일 통째 전달 금지.
- 독립 작업은 병렬 발주. 정기 산출(밸류에이션·팀·sitemap)은 스크립트+Actions로 이관(기본값). LLM은 스크립트가 못 하는 것만.
- KPI: 인사기록 기여 막대에서 Fable 비중↓, Opus·Sonnet·Haiku↑ (§8-4와 일치).

### 10-6. 충원 원칙 + 보안 상시화
- 충원은 최소 — 검수관 1명 외 신규 없음. 백엔드·트랙션 발생 전까지 운영·데브옵스·PM 불요.
- 보안은 사안별 → **월간 정기 점검**으로 전환(노출 스캔·deploy.yml SHA 고정 오너).
