# 개발 모드 — FAST DEV / CHECKPOINT / RELEASE CHECK

**감독 지시 2026-08-12**: *"작은 수정에 많은 대기시간은 개발효율이 낮아."*

이 문서가 개발 모드 규칙의 **SSOT** 다. `CLAUDE.md` 는 이 파일을 가리키기만 하고
조항을 다시 적지 않는다(값 미러링 금지).

---

## 기본 원칙 (감독 지시)

개발 중의 **빠른 시각 확인**과 PR/배포용 **전체 검증**을 분리한다.
**기본 상태는 항상 FAST DEV MODE 다.**

감독이 다음 중 하나를 명시적으로 말하기 전에는 전체 릴리스 검증을 실행하지 않는다:

> `검증해` · `전체 검증` · `PR 준비` · `머지 준비` · `배포 준비` · `RELEASE CHECK`

---

## 1. FAST DEV MODE — 기본

**목적**: 수정 → 실행 → 화면 확인 → 재수정의 반복 시간을 최소화한다.

수정 후:
1. 변경한 파일과 **직접 관련된 최소 검사만** 실행한다.
2. 가능하면 기존 dev server / hot reload 를 유지한다.
3. 감독이 결과를 확인할 수 있는 상태를 만든다.
4. 검사 결과와 확인할 화면만 **간단히** 보고하고 멈춘다.

### 금지 — 감독이 별도로 요청하지 않는 한

- 전체 gate · 전체 smoke · 독립 full smoke · 전체 test suite
- GitHub Actions 완료 대기
- 검수관 호출
- 배포 · main merge · main 직접 push

### ⚠ 사건 트리거는 모드와 무관하게 유효하다 — 매직워드를 기다리지 않는다

위 금지 목록에 「검수관 호출」이 있지만, **`.claude/agents/release-reviewer.md` 의
「언제 불리는가 (트리거)」가 정한 사건 트리거는 FAST DEV MODE 에서도 그대로 산다.**
그 트리거에 해당하면 감독의 매직워드를 기다리지 않고 검수관을 부른다.

**목록은 여기에 적지 않는다** — SSOT 는 그 파일 한 곳이다(팀장 조건 1).

왜 이 예외가 필요한가 (팀장 판정 2026-08-12, 검수관 지적으로 발견):

- 감독 지시의 목적은 *"작은 수정의 대기시간"* 감소다. 롤백 직후·보안 경계 변경·게이트
  FAIL 재시도는 **작은 수정의 반복 루프가 아니라 사고·보안 상황**이고, 금지 목록이
  거기까지 끄라는 뜻이라고 읽는 것은 확대 해석이다. **예외를 넣는 것이 지시의 목적을
  보존한다.**
- 경로 트리거(`.github/workflows/**` 등)는 CI 필수 상태검사와 `review-record.yml` 이라는
  **독립적 기술 백스톱**이 있어 매직워드를 깜빡해도 결국 걸린다. **사건 트리거는 그런
  백스톱이 0** 이고 전적으로 행위자 판단에 의존한다.
- 이 문서 첫 판본에는 이 예외가 없었고, 그러면 **"롤백 직후에도 매직워드 전에는 검수관을
  안 부르는 것"이 규정 준수**가 된다. `release-reviewer.md` 가 등급에 대해 경고한 그
  형태(*"등급이 검수관 호출을 그 순간에 꺼 버린다 — 롤백은 이미 사고를 낸 메커니즘"*)를
  **매직워드 부재로 재현**하는 것이다.
- 「①게이트 FAIL 재시도만 빼자」는 안은 팀장이 기각했다 — *"CI 가 이미 막는다"* 는 일부
  형태에서만 참이고(실패 원인을 우회한 수정은 CI 를 초록으로 통과할 수 있다), 사건
  트리거를 문서마다 다른 부분집합으로 적는 순간 그것이 **값 미러링 어긋남**이다.

### 최소 검사의 기준

변경이 시각적이거나 국소적이면 — 색상 · 조명 · 물 · 카메라 · 치비 크기/비율 ·
애니메이션 · 건물 높이 · 도로 폭 · UI 간격 · 텍스트 · 재질 —
**변경 파일 정적 오류 확인** + (필요하면) 관련 테스트만. 전체 smoke 를 매번 돌리지 않는다.

---

## 2. CHECKPOINT MODE — 기능 하나가 끝났을 때

트리거: `여기까지 체크` · `중간 검증` · `checkpoint`

1. 변경 diff 확인
2. 관련 lint/type 검사
3. 관련 테스트
4. 짧은 핵심 smoke 가 있으면 실행

목표 시간 **수 분 이내**. 전체 release smoke 와 GitHub CI 는 실행하지 않는다.

---

## 3. RELEASE CHECK — PR 직전

감독이 **명시적으로 요청한 경우에만** 전체 검증을 수행한다.

1. `git status`
2. 변경 파일 목록 확인
3. 예상하지 않은 scope creep 확인
4. diff 검토
5. 전체 gate
6. 필요한 full smoke
7. 검수관 게이트가 필요한 변경인지 판단
8. 필요하면 검수관 판정
9. PR 준비

**전체 검증 실패 시 임의로 우회하지 않는다.** 실패 원인을 수정한 뒤 필요한 검증만
다시 실행하되, **조건부 승인이면 반드시 검수관 재확인을 받는다**(구속력은 그대로다 —
근거는 `.claude/agents/release-reviewer.md` 의 「반려의 구속력」).

---

## 4. CI 역할

로컬은 **빠른 피드백**, CI 는 **전체 회귀 검증**.

PR CI 가 이미 full smoke 를 돌린다면 FAST DEV MODE 에서 같은 것을 반복하지 않는다.
**같은 10분짜리 검사를 로컬과 CI 에서 기계적으로 연속 두 번 돌리지 않는다.**

---

## 5. 브랜치 정책

`main` 은 배포/릴리스 브랜치다. 개발 중 시각 확인을 위해 `main` 에 직접 push 하지 않는다.
작업은 별도 브랜치에서 한다. `main` 진입 조건은 PR + 필요한 gate/CI/검수관 통과.

---

## 6. 수정 범위

바이브코딩 중에도 범위를 최소화한다. 감독이 요청하지 않은 **리팩터링 · 파일 이동 ·
이름 변경 · 새 abstraction · 새 dependency · 전역 상태 · schema 추가 · fallback 추가** 를
작업 편의를 이유로 같이 하지 않는다. 필요해 보이면 **먼저 이유를 보고한다.**

---

## 7. 보호 파일

`main.js` · `player.js` · `artworks.js` · `config.js` · SSOT schema · deploy workflow ·
security/CSP 관련 파일은 **필요한 경우에만** 수정한다. 국소 변경으로 해결되면 건드리지 않는다.

---

## 8. 구조 변경 트리거

다음은 FAST DEV MODE 라도 **RELEASE CHECK 단계에서 더 강하게 검토한다**:
schema 변경 · migration · 저장 데이터 구조 · P2P · privacy/security · CSP ·
deployment manifest · workflow · URL/base-path · world 구조 · 새 global state ·
새 dependency · 기존 실행 경로와 **병행하는** 새 실행 경로.

---

## 9. 작업 종료 보고 형식 (FAST DEV MODE)

길게 보고하지 않는다. 이것만:

```
변경:
- ...

빠른 검사:
- PASS / 미실행 + 이유

지금 확인할 것:
- ...
```

그리고 **감독의 시각 확인을 기다린다.** 전체 검증을 임의로 시작하지 않는다.

# ── 여기부터는 감독 지시가 아니라 이 환경의 실측이다 ──

위 규칙을 이 저장소에서 실제로 집행하려면 **무엇이 시간을 먹는지**를 알아야 한다.
안 그러면 병목이 아닌 곳에 규칙을 걸고 병목은 그대로 남는다.

## 실측 (2026-08-12, 이 컨테이너)

| 단계 | 소요 | 비고 |
|---|---|---|
| `npm run gate` (6종 전량) | **58초** | lint·typecheck·refs·gitadd·devlog-times·test |
| CI `verify` | 약 1분 | |
| CI `smoke`(`smoke:vite`) | **8~10분** | 필수 상태검사 |
| 병합 후 배포 반영(gh-pages) | 약 5분 | deploy 파이프라인이 smoke 를 한 번 더 돈다 |

**로컬 gate 는 병목이 아니다(58초).** 감독이 겪은 대기의 실체는 **CI smoke × 회차 +
배포 반영**이다. 오늘 하늘 작업 한 건에서 브랜치에 **4회 push** 했고 그때마다 CI 가
돌아 **약 40분**이 대기로 갔다.

## 그래서 실제로 줄여야 하는 것 — push 회차다

오늘 4회의 내역: ① 코드 ② 검수관 블로커 수정 ③ 문서(개발일지·게시판) ④ main 머지.
**②는 불가피**(검수관 판정 후 수정)하지만 **①③④는 한 번에 밀 수 있었다.**

- **문서 커밋을 코드와 따로 밀지 않는다.** 문서만 바뀌어도 CI 전량이 돈다.
- **main 정렬을 먼저 한다.** 착수 전 `git fetch && git merge origin/main` 이 이미
  규율인데(`CLAUDE.md` 「브랜치 위생 선제」) 오늘 안 지켜서 병합 직전에 충돌이 나
  push 가 한 번 더 늘었다.
- **CI 를 기다리는 동안 다른 일을 한다.** 오늘 검수관·조사 위임을 CI 와 겹쳐 돌린 것은
  맞게 한 것이다(브라우저를 안 쓰는 작업끼리는 겹쳐도 된다 — `CLAUDE.md` 참조).

## ⚠ 성립하지 않는 항목 하나 — 정직하게 적는다

감독 지시 1-2·1-3 의 *"dev server / hot reload 유지"* · *"사용자가 즉시 브라우저에서
결과를 확인"* 은 **이 환경에서 그대로는 성립하지 않는다.**

- 이 세션은 격리된 원격 컨테이너에서 돌고, **감독은 그 안의 dev server 에 접속할 수 없다.**
  (`localhost:5173` 은 컨테이너 내부다. 외부 노출 경로가 없다.)
- 감독은 대개 모바일에서 확인한다.
- 따라서 **감독의 화면 확인 = 라이브 배포**이고, 배포에는 위 실측대로 15~20분이 든다.

**이 문장을 안 적어 두면 다음 사람이 "즉시 확인" 을 지키려다 못 지키고, 못 지킨 것을
지킨 것으로 적는다.** 이 저장소의 상습 실패 형태다.

### 그러면 FAST DEV MODE 는 여기서 무엇인가

배포를 없앨 수 없으므로 **배포 1회당 판정 수를 늘린다.** 이미 채택돼 효과가 실증된
처방이 있다 — **URL 노브**(`docs/DEVLOG.md` 2026-08-12 항목, 71개 목록).

- 값·색·거리처럼 화면으로만 판정되는 것은 **후보를 노브로 3~4개 열어 한 번에 배포**한다.
- 감독은 링크 몇 개를 탭해서 비교하고 고른다. **확정값을 굽는 것은 그 다음 배포 1회.**
- 즉 FAST DEV MODE 의 성공 조건인 *"감독이 다음 판단을 바로 할 수 있음"* 을,
  이 환경에서는 **"한 번의 배포로 여러 판정을 받을 수 있게 만든다"** 로 읽는다.

이것은 **내(부팀장) 해석이지 감독 지시가 아니다.** 감독이 다르게 판정하면 그것이 최종이다.

## pre-commit 게이트는 유지한다 — 근거

FAST DEV MODE 는 "전체 gate 금지"를 적고 있고, 이 저장소의 pre-commit 훅은 `npm run gate`
스탬프가 없으면 커밋을 막는다. 둘이 부딪히는 것처럼 보이지만 **유지하는 쪽으로 읽는다**:

1. **58초다.** 감독이 지적한 "많은 대기시간"의 실체가 아니다.
2. **커밋이 유일한 안전망이라는 것이 오늘 실증됐다.** 같은 날 워킹트리가 두 번 무너졌고
   (executor 의 `git checkout HEAD --`, 브랜치 ref 가 gh-pages 로 덮어써진 원인 미상 건),
   **커밋·푸시해 둔 것만 살아남았다.** 미커밋 문서 편집 둘은 그대로 유실됐다.
   커밋을 미루는 방향의 최적화는 이 사고를 다시 부른다.

**단 커밋을 안 할 거면 gate 도 안 돌린다** — 화면만 보려고 고친 중간 상태에 58초를
반복해서 쓰지 않는다. gate 는 **커밋 직전 1회**다.
