## 원문

Open Art Show — 뉴욕 갤러리 거리 구현 지시서

아래 지시를 팀장에게 전달해 아트 방향 설정, 작은 구역 구현, 시각·기능·성능 검증까지 실행하라.

1. 목표와 판단 기준

오픈 아트쇼에 사람들이 걷고, 갤러리에 들어가고, 작품을 감상하며 자신의 전시를 만들 수 있는 뉴욕풍 갤러리 거리를 구현하라. 모바일 브라우저에서도 가볍게 실행되면서, 현대 RPG의 공간 연출에 익숙한 방문객에게 인상적인 첫 경험을 제공하는 것이 목표다.

환경 텍스처 해상도와 모델 복잡도를 올리기 전에 건축 비례, 실루엣, 조명, 재질 구분, 시선 유도, 작품의 존재감을 완성하라. 완성도는 코드 분량이나 추가한 오브젝트 수로 평가하지 않는다. 실제 플레이 화면과 동작으로 평가한다.

첫 목표는 약 5070m 거리, 서로 다른 인상의 건물 외관 6개, 실제 입장 가능한 1층 갤러리 1개, 교체 가능한 작품 812점이다. 이는 제안하는 초기 범위이며 저장소의 실제 좌표·이동 속도에 맞춰 조정하라. 이 구역이 기준을 통과한 뒤 다른 갤러리로 확장한다.

2. 시작할 때 확인할 것

1. 저장소의 AGENTS.md, 실행 지침, package/lock 파일, 현재 분기와 수정 내용을 읽는다. 현재 사용하는 엔진·버전·렌더러·후처리·에셋 로더·갤러리 배치·작품 저장 구조를 실제 코드로 확인한다.
2. 앞선 프로젝트 방향은 Three.js 기반, WebGL 운영 경로와 WebGPU 실험 경로 병행이었다. 이것을 현재 구현 상태로 단정하지 말고 실제 코드와 대조한다. 렌더러 교체나 의존성 최신화는 이번 작업의 기본 해법으로 삼지 않는다.
3. 기존 이동, 갤러리 입장, 작품 설치, 로그인·회원가입, 로그인 없는 관람, 저장, 하늘·시간대 선택 중 실제 존재하는 기능을 짧게 목록화하고 통합 지점을 정한다.
4. 제공된 캡처는 시각적 출발점이다. 캡처에서 창문·출입구가 드문 단순 건물 덩어리, 매우 어두운 길, 반복되는 잔디 띠, 거리의 목적지를 찾기 어려운 구도를 관찰할 수 있다. 원인이 조명·색 공간·임시 에셋·로딩·LOD 중 무엇인지는 코드와 실행 화면으로 확인한다.
5. 변경 전 실제 화면, 이동 경로, 로딩 용량과 프레임 시간 기준값을 남긴다. 실행하지 못했거나 실기기가 없으면 그 항목을 미검증으로 기록한다.

분석 보고서만 작성하고 종료하지 말고, 독립된 작업 브랜치에서 첫 구역 구현과 로컬 검증까지 이어가라. 일반적인 구현 선택은 팀 내에서 해결한다. 외부 공개 배포는 기존 프로젝트의 승인 규칙과 사용자에게 이미 받은 권한을 따른다.

3. 아트 디렉션: New York Gallery Walk

소호풍의 리듬 있는 건물 외관과 첼시 갤러리의 차분한 전시 공간을 결합한 창작 거리다. 실제 특정 도로를 그대로 복제하는 프로젝트는 아니다. 기본 시간은 갤러리 오프닝을 앞둔 늦은 오후로 한다.

디자이너는 구현 전에 컬러 팔레트, 건물 비례, 조명 방향, 대표 시점, 사용하는 외관 모듈, 피해야 할 시각적 패턴을 한 장 분량의 아트 기준으로 작성한다. 레퍼런스는 전체 분위기뿐 아니라 창틀 깊이·보도·입구·전시실처럼 항목별로 연결한다.

공간을 알아보게 하는 중간 크기 요소부터 만든다. 창과 문, 층 구분, 보도 경계가 없는 상태에서 작은 풀, 벽돌 얼룩, 반짝임을 늘리지 않는다. 강한 블룸·짙은 안개·깊은 암부로 미완성 부분을 가리는 방식도 합격으로 보지 않는다.

4. 방문객이 감탄할 장면 세 곳

1. 처음 접속한 거리: 건물들이 만드는 원근과 따뜻한 햇빛 속에 갤러리 간판과 안쪽 대형 작품이 함께 보인다. 시작 카메라는 하늘만 크게 보이거나 바닥만 보이는 구도를 피한다.
2. 갤러리 문 앞: 실외의 따뜻한 거리와 실내의 차분한 흰 벽이 대비되고, 작품이 실제 벽에 걸려 있음을 알 수 있다. 입장 가능한 문은 형태와 표시로 명확히 구별된다.
3. 작품 앞에서 돌아본 장면: 액자의 얇은 두께, 벽과의 간격, 전시실의 깊이, 창밖 거리가 함께 보인다. 한 시점에서만 멋있는 세트가 되지 않도록 반대 방향과 이동 중에도 검토한다.

첫 구역에서 이 세 장면을 우선 완성한다. 이후에 작은 안뜰, 옥상 정원, 카페 등 추가 공간을 검토한다.

5. 갤러리와 작품 설치 기능

입장 가능한 건물의 1층은 문·바닥·벽·천장·충돌 영역을 갖춘 실제 공간으로 만든다. 첫 갤러리에서는 최소한 거리에서 입장 → 작품 선택 → 상세 감상 → 다시 거리로 나오는 동선이 이어져야 한다.

실내 전체를 항상 로드할 필요는 없다. 접근 시 입구 주변과 실내를 미리 로드하고, 먼 실내는 단순한 프록시와 썸네일로 처리한다. 전환은 실제 문 위치와 일치시켜 빈 공간, 작품의 순간 소실, 검은 로딩 화면이 눈에 띄지 않도록 한다. 내부에서 창밖을 볼 수 있는 만큼의 거리도 유지한다.

작품 설치는 다음 흐름으로 구현하라.

• 전시 편집 모드에서 벽이나 전시 슬롯 선택 → 이미지 업로드 또는 기존 작품 선택 → 크기·위치·액자 지정 → 저장 → 새로고침 후 복원.
• 기존 작품·저장 모델이 있으면 그 구조를 확장한다. 새 시스템이 필요하면 건물 ID, 전시실 ID, 벽/슬롯 ID, 작품 ID, 위치, 표시 크기, 액자 설정의 관계를 저장 데이터로 분리한다.
• 임의 벽 배치보다 미리 정의한 전시 슬롯을 먼저 완성해 벽 밖 배치·관통·겹침을 줄인다. 이후 필요하면 자유 배치를 추가한다.
• 가로형·세로형·정사각형을 모두 원본 종횡비로 표시한다. 기본값은 잘림 없는 맞춤이며 사용자가 선택한 자르기만 허용한다.
• 액자와 작품은 교체 가능해야 한다. 다른 작품으로 바꾸는 데 건물 GLB 재생성이나 소스 수정이 필요하면 안 된다.
• 기존 서버 저장과 권한 체계가 있으면 연결한다. 없다면 로컬 시연 저장과 공개 전시·계정 간 공유를 구분하고, 로컬 저장만 되는 기능을 공개 전시 완료로 보고하지 않는다.
• 파일 오류, 잘못된 형식, 로딩 실패는 이해하기 쉬운 안내를 제공하고 기존 전시 상태를 유지한다.

전시 작품은 색 표현이 중요하다. 환경의 노을색·노출·블룸·톤매핑이 작품의 색과 대비를 과도하게 바꾸지 않도록 전용 표시 경로를 설계하라. 일반적인 sRGB 이미지에 맞는 입력/출력 색 변환을 확인하고, 다른 프로파일 입력은 지원 범위와 정규화 정책을 정한다. 상세 감상은 장면의 분위기 조명 영향을 받지 않게 한다. 이 항목은 장치마다 완벽한 색 일치를 보증한다는 뜻은 아니다.

원본 이미지는 보존하되 공간에서는 화면 점유율에 맞는 축소본을 사용하고, 선택한 작품만 필요할 때 상세 이미지를 로드한다. 분위기용 벽·바닥 텍스처와 작품 이미지의 로딩 정책을 분리한다.

|빛과 그림자|모바일은 필요한 범위의 주광 그림자 1개를 출발점으로 한다. 갤러리 조명은 베이크나 저비용 벽면 명암부터 검토하고 작품마다 그림자 광원을 만들지 않는다.          |
|시간대   |베이크된 방향성 그림자와 실제 하늘/태양 방향이 어긋나지 않게 한다. 기존 시간대 기능에 맞춰 중성 AO, 제한된 실시간 그림자, 조명 프리셋을 조합한다.         |
|유리    |가까운 1층 전면 창만 실내 가시성을 살린다. 실제 투명도가 필요 없는 상층 창은 단순 반사·깊이 표현으로 처리한다.                              |
|반사·후처리|환경맵 같은 저비용 방식부터 사용한다. 실시간 반사, SSR, SSAO, 볼류메트릭 효과는 기본 전제에 넣지 말고 측정된 이득과 비용으로 결정한다.             |
|식재    |가까운 위치 위주로 배치하고 과도한 투명 면 겹침을 피한다. 원거리 LOD와 밀도를 조절한다.                                           |
|거리 로딩 |가까운 구역과 현재 전시실 중심으로 로드하고, 퇴장 후 재사용 캐시에는 크기 상한을 둔다.                                             |
|텍스처 전송|환경용 KTX2/Basis 지원을 현재 로더와 장치에서 검증한다. 파일 크기와 GPU 상주 메모리를 각각 평가한다.                               |
|렌더 해상도|CSS 표시 크기와 실제 drawing buffer를 구분한다. DPR 상한 또는 픽셀 수 예산을 두고 성능에 따라 조절한다. 작품 상세 UI의 선명도는 별도로 관리한다.|

메시 압축으로 다운로드가 작아졌다고 삼각형 수·그리기 호출·GPU 비용이 함께 줄었다고 보고하지 않는다. 최적화 효과는 실제 지표로 검증한다.

7. 초기 성능 예산

아래 수치는 이 프로젝트의 출발용 제안값이다. 현 상태의 측정값, 보장 성능, 모든 장치의 공통 한계가 아니다. Baseline 단계에서 확보 가능한 기준 장치와 브라우저를 명시하고, 달성 가능한 예산으로 한 번 조정한 후 그 예산을 고정해 비교한다. 이후 기준을 바꿀 때는 이유와 이전/새 수치를 남긴다.

|지표                  |모바일 출발 목표                          |데스크톱 출발 목표                    |
|--------------------|-----------------------------------|------------------------------|
|실제 이동 중 프레임         |지속적인 30fps를 목표, 프레임 간격 p95 ≤ 33.3ms|60fps를 목표, 프레임 간격 p95 ≤ 16.7ms|
|시작 시 렌더 DPR 상한      |1.25                               |1.5                           |
|화면 1프레임 전체 draw call|150 이하                             |250 이하                        |
|화면 1프레임 렌더 삼각형      |20만 이하                             |40만 이하                        |
|초기 관람 가능 구역의 전송량    |10MiB 이하                           |같은 초기 로딩 경로 우선                |
|환경 텍스처의 일반 크기       |512~1024px                         |공유 에셋 유지                      |

보조 조건:

• 첫 관람 가능 시점의 전송량은 필요한 JS·디코더·모델·환경 텍스처·작품 축소본을 포함한다. 시작 직후 강제로 이어받는 에셋을 숨겨 초기 용량만 작게 보고하지 않는다.
• 1회 냉시작 로딩, 안정화 후 고정 이동 경로, 3분 연속 실행, 동일 갤러리 3회 재입장을 기준으로 확인한다. 장치·브라우저·렌더러·화면 크기·실제 렌더 크기·품질 프리셋·네트워크 조건을 함께 기록한다.
• 평균 FPS와 함께 프레임 간격 p95, 로딩/입장 시 끊김을 보고한다. GPU 타이머가 없으면 프레임 간격을 GPU 실행 시간이라고 부르지 않는다.
• 텍스처/geometry 개수와 크기 기반 GPU 메모리 추정치를 보고한다. renderer.info.memory의 texture 개수는 바이트 수가 아니다. 정확한 GPU 메모리를 읽지 못하면 추정이라고 표시한다.
• 후처리 등 여러 render 호출이 있으면 실제 프레임 전체의 호출/삼각형이 집계되는지 확인한다. 렌더러마다 통계 정의가 다를 수 있으므로 집계 범위를 명시한다.
• 데스크톱 브라우저의 모바일 viewport는 화면 배치 확인용이다. iPhone Safari/Android Chrome 실기기 성능을 검증한 것으로 취급하지 않는다. 소프트웨어 렌더러의 결과도 실제 GPU 성능과 구분한다.
• 예산 초과 시 프로파일을 보고 해결한다. 오브젝트가 원인이면 병합/인스턴싱/컬링, 픽셀 비용이면 투명도·후처리·그림자·해상도, 메모리면 텍스처/실내 로딩을 먼저 조정한다. 작품 가독성과 길 찾기에 필요한 형태를 무조건 희생하지 않는다.

8. 팀 역할과 작업 소유권

모델 이름은 사용자 팀에서 쓰는 명칭을 그대로 사용한다. 아래 배정은 모델 성능 순위를 주장하는 것이 아니라 작업 책임을 나누는 규칙이다.

|역할    |담당                  |산출물과 책임                                                   |
|------|--------------------|----------------------------------------------------------|
|팀장    |페블 5.1              |범위, 작업 순서, 파일 소유권, 공통 상태, 다음 반복의 상위 문제 3개, 최종 수용 여부를 관리한다.|
|부팀장   |현재 팀에 배정된 최신 Opus   |실제 코드 구조 확인, 엔진/저장/좌표 인터페이스, 통합 설계와 통합 커밋, 기술 리뷰를 담당한다.   |
|아트 디렉터|현재 팀에 배정된 최신 디자이너 모델|비례·팔레트·조명·카메라 기준을 작성하고 매 반복 실제 캡처를 보고 위치가 특정되는 수정 지시를 한다. |
|환경 구현 |환경/3D 담당 멤버         |건축 모듈, 거리, 소품, 재질, 조명, LOD를 구현한다.                         |
|전시 기능 |UI/데이터 담당 멤버        |출입, 벽/슬롯 배치, 업로드·교체·저장·복원, 작품 감상을 구현한다.                   |
|QA·성능 |구현과 독립된 검증 멤버       |고정 경로 재현, 캡처·영상·지표·오류 수집, 기능/성능 통과 여부를 판정한다.              |

병렬 작업 전에 공유 인터페이스를 정한다. 최소한 건물/문/벽/작품 ID, 좌표계와 단위, 실내 진입·퇴장 이벤트, 품질 프리셋, 저장 인터페이스가 필요하다. 실제 코드에 맞춰 필요한 것만 확정한다.

각 멤버에게 수정 가능한 파일/모듈을 배정한다. 동일 파일을 동시에 수정하지 않는다. 공통 렌더러와 공용 설정 변경은 부팀장이 순서대로 통합한다. 구현자가 자기 결과의 유일한 평가자가 되지 않게 한다. 멤버가 부족하면 같은 모델의 별도 검토 세션이라도 구현 설명을 그대로 승인하는 방식은 피한다.

9. 하네스: 재현 가능한 평가 장치

여기서 하네스란 특정 프레임워크 이름이 아니라, 같은 장면을 자동으로 실행하고 화면·기능·성능 증거를 남기는 검증 장치다. 기존 프로젝트의 브라우저 자동화와 테스트 도구를 우선 재사용한다. 필요하면 Playwright 같은 도구로 최소한의 실행 경로를 추가한다.

저장소 관례에 맞는 경로를 사용하되 다음 종류의 기록을 남긴다. 아래 이름은 산출물 예시이며 실제 기능 파일 경로를 강제로 바꾸라는 의미가 아니다.

• art-direction.md: 팔레트, 대표 화면, 건축/조명 기준, 레퍼런스.
• tasks.md: 담당자, 소유 파일, 의존성, 현재 단계.
• acceptance.md: 시각·기능·성능 합격 조건.
• state.md: 마지막 통과 커밋, 이번 변경, 남은 문제, 다음 행동.
• evidence/iteration-XX/: 화면, 영상, 지표 JSON, 콘솔 오류, 검토 기록.

고정 캡처 시점은 거리 시작, 대표 외관 근접, 입구에서 실내 보기, 실내 전체, 작품 근접, 실내에서 거리 보기의 6곳으로 한다. 동일한 카메라 위치·방향·FOV·viewport·품질·시간대·에셋 로딩 상태로 전후를 비교한다. 프로시저럴 요소는 seed를 고정하고, 움직이는 요소는 캡처 시각을 맞추거나 평가 중 잠근다. 자동 노출이 있으면 비교 조건을 고정한다.

대표 정지 화면 외에 약 30초의 거리 → 갤러리 → 작품 → 거리 이동을 확인한다. 정지 화면은 비례·색·구도를, 이동은 팝인·충돌·깜빡임·출입 전환을 평가한다. 이 기록과 별개로 성능 측정 경로를 실행한다.

디자이너와 QA는 이미지 파일을 실제로 열어 확인해야 한다. 이미지 열람이나 브라우저 실행 도구가 없으면 부족한 검증을 명시한다. 코드만 읽고 화면을 봤다고 보고하거나 생성형 콘셉트 이미지를 실행 화면으로 제출하지 않는다.

10. 반복 작업 방식

Baseline: 현 상태와 공통 계약

실행 상태 확인 → 기존 기능과 코드 구조 파악 → 기준 화면·성능 수집 → 아트 기준과 인터페이스 확정.

이 단계에서 시작 위치의 밝기 문제를 발견하더라도 조명 값을 임의로 올리기 전에 색 공간, 에셋 로딩, 재질 입력을 확인한다.

반복 1: 형태·빛·구도

짧은 거리, 대표 갤러리 외관, 최소 실내와 예시 작품을 구현한다. 건물 비례, 창/문 깊이, 보도, 재질 구분, 기본 조명을 먼저 완성한다. 작은 장식의 대량 추가는 다음 단계로 미룬다.

반복 2: 출입·전시·완성도

입장과 재퇴장, 작품 설치/교체/저장, 가로/세로 작품, 작품 색, 모바일 조작을 완성한다. 대표 외관을 다른 입면으로 확장하고 선택된 소품을 추가한다.

반복 3: 성능·통합 검증

첫 로딩, 실내 프리로드, LOD, 투명도, 그림자, DPR, 메모리 회수를 측정하며 조정한다. 기능 회귀와 6개 시점, 이동 영상으로 기준을 검증한다.

각 반복 안에서는 다음 규칙을 지킨다.

1. 구현하고 실제 실행한다.
2. 같은 조건의 캡처·동작·성능 증거를 수집한다.
3. 디자이너가 화면에서 가장 큰 문제를, QA가 기능·성능의 실패를 기록한다.
4. 팀장은 사용자 체감이 큰 문제 상위 3개를 선정한다. 새 기능을 계속 추가해 검토 대상을 넓히지 않는다.
5. 담당자에게 문제 위치, 원인 가설, 바꿀 항목, 재검토할 장면을 지정한다.
6. 수정 후 해당 증거를 다시 수집한다. 기능·성능·시각 중 하나를 악화시켰으면 그 차이를 남긴다.
7. 합격 조건을 충족하면 구역을 확장한다. 같은 문제가 3번 연속 개선되지 않으면 마지막 통과 상태를 보존하고, 원인·시도 결과·범위 축소 또는 설계 변경 대안을 팀장이 결정한다. 사용자 결정이 필요한 외부 제약만 구체적인 선택지와 함께 보고한다.

반복 횟수와 진행 단계는 구분한다. 무한 반복이나 근거 없는 '95점까지 개선'을 완료 조건으로 삼지 않는다. 개선 전후의 실제 차이와 합격 조건이 기준이다.

검토 의견의 예:

> '거리 시작 화면의 왼쪽 건물 1층이 그늘에서 하나의 검은 면으로 합쳐진다. 문틀 깊이를 주고 입구 주변의 명암 분리를 조절하라. 전체 노출을 올리지는 말고 같은 시점에서 출입구가 읽히는지 확인하라.'

단순히 '더 고급스럽게', '더 게임처럼', '퀄리티 업'이라고 지시하고 종료하지 않는다.

|전시   |서로 다른 종횡비의 작품을 설치·교체하고 저장/새로고침으로 복원한다. 작품을 바꿔도 건물 에셋을 다시 만들지 않는다.                       |
|작품 품질|그림이 잘리거나 늘어나지 않는다. 확대 감상에서 노을색·블룸 때문에 작품 색과 대비가 크게 바뀌지 않는다.                             |
|성능   |정한 기준 장치와 품질에서 프레임/로딩 예산을 통과한다. 반복 입장 후 리소스가 캐시 상한을 넘어서 계속 증가하지 않는다. 미확보 실기기는 미검증으로 남긴다.|
|기존 동작|실제 존재하는 관람·계정·저장·시간대·조작 흐름이 지정한 검증 경로에서 동작한다.                                           |
|보고   |코드 변경, 실행 명령, 전후 화면, 동작 증거, 성능 표, 남은 제한이 서로 일치한다.                                       |

사진 같은 렌더링을 약속하지 않는다. 낮은 환경 해상도에서도 건축과 조명이 설계되어 있고, 작품을 실제로 전시할 수 있으며, 이동 중에도 일관된 품질이 유지되는 상태를 목표로 한다.

12. 최종 보고 형식

1. 구현된 방문 경험을 3문장으로 설명한다.
2. 6개 대표 시점의 전후 화면과 실제 이동 영상 또는 재현 경로를 제시한다.
3. 사용 장치·브라우저·렌더러·화면/렌더 크기를 밝힌 성능 비교 표를 제시한다.
4. 작품 설치·교체·저장·복원과 출입 검증 결과를 제시한다.
5. 변경 파일, 로컬 실행 방법, 마지막 검증 커밋을 제시한다.
6. 미검증 항목, 알려진 문제, 다음 거리 확장에 재사용할 모듈을 간단히 남긴다.

지금 실제 저장소를 읽고 Baseline부터 시작하라. 이어서 첫 구역을 구현하고 검토 증거까지 만들어라.

참고 자료

참고 자료는 구현 원리와 시각 언어의 근거다. 위 구역 크기·역할 배정·예산 수치는 이번 작업을 위한 제안이며 출처에서 제시한 보장값이 아니다. API 세부사항은 저장소에 설치된 버전과 대조한다.

• 같은 정적 요소를 묶어 그리기 요청을 줄일 수 있으며, 병합 후 개별 이동에는 제약이 있다: Three.js — Optimize Lots of Objects.
• 그림자 비용과 단순화된 그림자 표현을 검토할 때: Three.js — Shadows.
• 색 텍스처, 데이터 텍스처, 작업 공간, 출력 공간을 구분할 때: Three.js — Color Management.
• CSS 크기와 실제 렌더 픽셀 수를 구분할 때: Three.js — Responsive Design.
• 프레임 통계 집계와 리소스 개수의 의미를 확인할 때: Three.js — WebGLRenderer.
• 텍스처 전송량과 GPU 메모리를 줄이는 압축 형식의 원리: Khronos — KTX 2.0 and glTF.
