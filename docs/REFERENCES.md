# 레퍼런스 지식베이스 — 유사 오픈소스 벤치마크

> 🧭 **레퍼런스 분석가**(계약직)의 상설 지식베이스. 우리와 같은 결(브라우저/웹 3D 가상공간·멀티유저)의
> 검증된 오픈소스 5종을 분석해, 우리가 기술 난관에 부딪힐 때 "바퀴 재발명" 없이 검증된 해법을 참조한다.
>
> **철칙 — 코드가 아니라 설계를 빌린다.** 외부 저장소의 코드·에셋·GLB·텍스처는 절대 반입하지 않는다
> (§IP 규율 + 자기완결). 수치·기법·아키텍처 원리(저작권 대상 아님)만 취해 **우리 코드로 독립 재구현**한다.
> 특히 hyperfy는 **GPL-3.0**(강한 카피레프트)이라 코드 복사 시 배포물 전체가 전염 — 아이디어만.

분석일: 2026-07-22 (초기 스터디, 감독 지시) · 2026-07-26 (5종 Claude-of-Duty 추가, 감독 지시).

## 1) hyperfy — 클라이언트 렌더 최적화의 교본

- **아키텍처**: 강한 클라/서버 분리, 서버 SSOT + 전체 스냅샷 후 증분 동기화, 서버권위, DB 60초 배치 upsert.
- **성능 심장 `Stage.js`**:
  - **자동 인스턴싱 배칭** — `geometry.uuid + material.uuid + castShadow/receiveShadow`를 키로 동일 조합 메시를
    하나의 `InstancedMesh`로 자동 통합. 인스턴스 삭제는 마지막 요소와 swap(단편화 방지).
  - **Uber Shader** — GLSL 동적 확장으로 인스턴스별 emissive를 단일 셰이더 컴파일로(머티리얼 변형 폭발 방지).
  - **LooseOctree** 공간 인덱싱(레이캐스트·컬링 가속).
  - **LOD 프레임 분산** — `LODs.js`가 프레임당 `BATCH_SIZE=1000` 노드만 커서 순회(스파이크 방지).
    거리 기반 레벨 선택, `scaleAware` 정규화. ⚠️ **히스테리시스 없음** → 우리는 전환 여유대역 필수 추가.
  - **DPR 런타임 동적 조정**, N8AO 반해상도(`halfRes`), ACES 톤매핑, HalfFloat FBO.
- **차용 불가**: 서버권위·DB·JWT·PhysX WASM·LiveKit SFU·전체 스냅샷 초기전송(우리 성능난에 역행)·GPL 코드복사.

## 2) Hubs — 갤러리 용례 최근접, 서버는 버리고 클라 기법만

- **전시 플랫폼으로 검증**: WHO 미술 가상미술관·bitforms·RIBA 건축전·Ars Electronica 등 실사례 풍부.
- **아키텍처(서버 중심, 우리와 정반대)**: Reticulum(Elixir/Phoenix, 아바타 transform WebSocket 릴레이) +
  Dialog(mediasoup **WebRTC SFU** 음성/영상 중계) + Nearspark/Farspark(외부 미디어 프록시). 방 24명 상한.
- **성능 기법(전부 정적·무백엔드 양립)**:
  - **KTX2 / Basis Universal 텍스처 압축**(`hubs-glb-tools`, glTF-Transform) — GPU 메모리에 **압축된 채 상주**해
    VRAM·업로드시간 급감(JPEG/PNG는 GPU에서 해제되어 상주). ETC1S(용량)/UASTC(품질·노멀맵)/Auto.
  - **three-batch-manager** — 텍스처 아틀라스 + instance uniform을 UBO에 담는 정적 배칭(씬을 소수 드로우콜로).
  - **씬 예산**: ~50k 삼각형 권장, 총 에셋 70MB↑는 폰 비현실적, 텍스처는 **2의 거듭제곱**(안 맞으면 폭증).
  - **런타임 계측**: 우하단 FPS 미터 → 로드시간·삼각형·텍스처 수 실시간(제작자가 예산초과를 눈으로).
- **차용 불가**: Reticulum·Dialog SFU·미디어 프록시·CDN 배포·Spoke 서버 발행(전부 상시 서버 필요).

## 3) Decentraland SDK7 — "동시 렌더 삼각형" 예산 강제

- **ECS 씬 모델**: Entity(ID) + Component(순수 데이터) + System(함수). **우리 `space.ts`는 이미 데이터지향**이라
  ECS의 절반(데이터/로직 분리)을 사실상 달성 — 정적 씬엔 ECS 런타임 전면 도입 불필요.
- **★예산 강제 모델(파셀 n개 기준)★**: 삼각형 `n×10,000`, 엔티티 `n×200`, 재질/텍스처/높이는 **log2**(넓혀도
  거의 안 늘어 GPU 상태전환 억제).
- **★결정적 규칙: "현재 렌더링 중인 엔티티만 카운트"★** — 예산은 "총 자산량"이 아니라 **"임의 순간 화면에 올라오는
  삼각형 수"** 기준. → 총량 축소가 아니라 **동시성 축소**가 성능의 정답 방향.
- **빌더 예산 미터**: 크리에이터가 배포 전 한도를 게이지로 봄(성능을 런타임 아닌 **저작 시점에 강제**).
- **차용 불가**: ECS 런타임 전면 도입(정적 씬엔 과잉)·격리 JS 샌드박스·카타리스트 배포·LAND 온체인.

## 4) Catalyst — 백엔드 진화의 참조(알맹이만 축약)

- **구성**: Content Server(엔티티 저장·동기화) + Comms(실시간 통신) + Lambdas(조회·검증) + Nginx.
- **알맹이 3구조(탈블록체인)**:
  - **① 콘텐츠 주소화** — 파일을 **해시(IPFS CID)로 저장** → 중복제거·불변 이력·CDN 캐싱이 공짜.
    우리 "파라미터가 곧 공간"과 정합(공간 JSON을 해시하면 그 자체가 영구 참조 ID).
  - **② 포인터DB / 파일스토리지 분리** — DB엔 "누구의 어떤 공간이 현재 어떤 버전(해시)인가"만, 큰 파일은 오브젝트 스토리지.
  - **③ 서명 기반 배포 권한(Auth Chain 축약)** — 비밀번호 DB 대신 **소유권 서명**. 배포검증 = 서명+해시무결성+용량.
- **실시간**: 근세대는 BFF+**Archipelago(근접 인원을 "섬"으로 클러스터링)**+LiveKit SFU+NATS. 구세대는 **PeerJS 시그널링**.
  → 우리에 SFU는 과하나 **"근접 기반 방/섬 분리"**는 소규모 P2P에서도 유용.
- **차용 불가(우리 규모에 과함)**: 블록체인·DAO 노드승인·The Graph 온체인·LiveKit 클러스터·NATS·다중노드 연합.

## 5) Claude-of-Duty — 셰이더 예열·머티리얼 순열 통제의 교본 (MIT)

`mshumer/Claude-of-Duty` — 프롬프트 하나로 만들어진 three.js 단독 브라우저 FPS. **우리와 동류의 제약**을
공유한다: 정적 호스팅, 외부 서비스 0, 절차적 텍스처 생성(에셋 다운로드 없음), vite 빌드. 감독이 "프레임이
엄청 빠르다"며 레퍼런스로 지정(2026-07-26). MIT라 **hyperfy와 달리 전염 위험이 없다** — 다만 우리 철칙은
그대로다(설계 참고 후 독립 재구현).

**우리와 다른 것 — 비교할 때 반드시 전제할 것.** ①**WebGL**(우리는 WebGPU 메인 + WebGL 폴백)
②**고정 맵·스트리밍 없음**(우리는 24m 파셀을 걸으며 무한 로드) ③단일 작가 콘텐츠(우리는 사용자 생성).
즉 "프레임이 빠르다"의 상당 부분은 **로딩 화면에서 전부 올려버릴 수 있기 때문**이다. 우리가 9번 실패한
"승격 파셀의 첫 드로우" 문제는 그들에게 애초에 존재하지 않는다. 그럼에도 **예열 기법 자체는 배울 것이
많다** — 특히 아래 하나는 우리 3차 예열 실패의 원인을 정확히 설명한다.

- **★ 예열은 forward 패스만으로 끝나지 않는다** (`src/world/index.js` `prewarmMaterials()`).
  `renderer.compileAsync(scene, camera)`는 머티리얼의 **forward lit variant에만** 도달한다. 매 프레임 도는
  override 패스(그림자 캐스케이드의 `depthMaterial`, 프리패스의 gbuffer 재질)는 **별개 프로그램**이고,
  각각 plain / instanced / instanced+instanceColor 순열을 따로 갖는다. 그들은 `scene.overrideMaterial`을
  바꿔가며 compileAsync를 **패스마다 반복 호출**하고 `finally`로 복원한다(픽셀 중립).
  → **우리 3차 예열은 forward만 굽고 그림자 패스를 안 구웠다.** 개발일지 3차에 "그림자 깊이 렌더는
  compileAsync가 굽지 못하는 유일한 영역"이라 적어놓고도 대응하지 않은 것이 실패의 뿌리다.
- **예열 전에 주입을 끝낸다** — 재질에 CSM/AO/SSR 셰이더 주입을 먼저 적용한 뒤 컴파일한다. 그들 주석:
  *"the program we warm is not the program the frame will use"*. 주입 후 컴파일 순서가 뒤바뀌면 예열분이
  전부 캐시 미스가 된다.
- **라이트 개수를 예열 전에 고정한다** — 라이트 개수가 셰이더 순열을 바꾸므로, "프레임 루프가 실제로
  돌 개수"로 안정화한 뒤 컴파일한다(부팅 중 거리 컬링이 남긴 우연한 개수로 구우면 무효).
  → 우리도 `lightPool`로 개수를 고정했다고 믿었지만 파셀 경계에서 `lightsInUse`가 실제로 변한다.
- **부팅 시 전량 예열 오케스트레이션** (`src/core/prewarm.js`) — 프레임 루프 시작 **전에** 각 서브시스템
  (월드·무기·AI·FX·스카이)에게 예열 훅을 요청하고, `renderer.info.programs.length` 델타로 몇 개를 구웠는지
  보고받는다. 우리 조사에서 월드 전체가 **구조 키 13종**으로 접힌다는 정적 분석이 나왔으므로, 파셀 종류가
  유한한 우리도 부팅 예열이 원리적으로 가능하다.
- **적응 품질과 재컴파일의 충돌** — 확인 대상. 우리는 `shadowMap.enabled` 토글이 씬 전체 재컴파일을
  일으키는 자기모순이 있었다(성능 4차에서 수정). 그들이 품질 강등을 재컴파일 없이 하는 설계를 가졌다면
  그 방식이 우리 적응계의 다음 표적이다.

**차용 불가·주의**: ①WebGPU에서 `scene.overrideMaterial` + `compileAsync`의 의미가 WebGL과 같은지는
**별도 확인 필요**(three의 WebGPU 경로는 노드 기반이라 프로그램 순열 모델이 다르다). ②고정 맵 전제의
기법(로딩 화면 전량 업로드)은 스트리밍 구조에 직접 이식할 수 없다 — 우리는 "부팅 예열 + 스트리밍 중
노출 분산"의 조합이 필요하다. ③FPS 특유의 것(무기 뷰모델·탄도·AI 전투)은 무관.

## 우리 적용 — 오픈월드 성능 난관 처방 (4개 소스 수렴)

당면 증상: 오픈월드 진입 시 **삼각형 8.4만 · 드로우콜 254 · pixelRatio 2**로 PC·모바일 버벅임.

| 순위 | 해법 | 출처 | 기대 효과 | 자기완결 |
|---|---|---|---|---|
| **1** (즉효·최소) | **모바일 DPR 상한 ≤1.5 + 동적 해상도 스케일** | hyperfy·hubs | pixelRatio 2→1.5, 모바일 픽셀 4배→2.25배 | ✅ 코드 몇 줄 |
| **2** (최대효과) | **파셀 정적 배칭 + 텍스처 아틀라스로 드로우콜 병합** | hyperfy 인스턴싱·hubs batch-manager | **254 → 수십** | ✅ 로컬 three |
| **3** | **"동시 렌더 삼각형" 예산 + 진입반경 LOD/컬링** | sdk7(렌더링분 카운트)·hubs(50k)·hyperfy(LOD분산) | 진입 8.4만 완화 | ✅ |
| **4** | **KTX2/Basis 텍스처 사전압축**(빌드 시점) | hubs(glTF-Transform) | 진입 히칭·VRAM 급감 | ✅ 빌드산물, CSP 무관 |
| **5** | **빌더 예산 미터 + 런타임 성능 HUD** | sdk7·hubs | 저작 시점에 과부하 차단 | ✅ (debug-perf.js가 이 방향) |

**주의**: hyperfy LOD는 히스테리시스가 없어 경계 깜빡임 가능 → 우리는 전환 여유대역을 반드시 추가.

## 우리 적용 — 백엔드 진화 로드맵 (Catalyst 축약, 중장기)

- **0단계(현재)**: GitHub Pages 정적 + peerjs P2P. 백엔드 0.
- **1단계**: 읽기전용 콘텐츠 서버 — 오브젝트 스토리지(S3/R2) + 얇은 조회 API. 공간 JSON을 **해시 파일명**으로 업로드.
- **2단계**: 아이덴티티 + 메타DB — PostgreSQL에 회원·공간 포인터(소유자→현재 해시)·배포이력. 인증은 이메일/OAuth+JWT.
- **3단계(필요 시)**: 서버권위 멀티플레이어 — **Archipelago식 방/근접 분리** 먼저, 부족하면 SFU 1대. NATS·다중노드·DAO는 불필요.
- **원칙**: Catalyst의 "탈중앙·연합" 겉껍질은 버리고 **콘텐츠 주소화 · 포인터/파일 분리 · 서명 배포검증** 세 알맹이만
  표준 웹(스토리지+PostgreSQL+JWT)으로 축약.
